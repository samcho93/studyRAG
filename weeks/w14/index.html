1학습 목표

이번 실습이 끝나면
  • 질문이 유사도 질문인지 조건 질문(개수·목록·범위)인지 구별하고, 순수 검색이 조건 질문에서 틀리는 이유를 설명할 수 있다.
  • 질문을 필터와 검색어로 나누는 셀프 쿼리를 규칙 또는 LLM으로 만들고, 허용 스키마로 검증할 수 있다.
  • 사전 필터·사후 필터·빈 결과 완화를 비교하고, 정밀도와 재현율로 효과를 측정할 수 있다.

2왜 필요한가

응용 1에서 만든 학과 안내 챗봇에 이렇게 묻는다고 하자. “화요일에 305호에서 하는 수업은?” 시간표를 행 단위 문장으로 바꿔 두었으니 BM25로 검색하면 top-3는 다음과 같다.

  1. ✓ 1학기 화요일 4~6교시에는 데이터베이스 수업이 305호에서 열린다.
  2. ✓ 2학기 화요일 1~3교시에는 검색증강생성(RAG) 시스템 구축 수업이 305호에서 열린다.
  3. ✗ 2학기 목요일 1~3교시에는 MLOps 수업이 305호에서 열린다.

세 번째 결과는 “305호에서”가 겹치고 “요일”이라는 글자도 겹쳐서 올라왔다. 검색은 얼마나 비슷한가로 순위를 매길 뿐, “화요일이어야 한다”는 조건을 확인하지 않는다. LLM이 이 세 문장을 받으면 목요일 수업까지 답에 넣을 수 있다.

검색은 조건을 모르고, 개수도 모른다

“2학기에 305호에서 하는 수업은 몇 개야?”의 정답은 4개(월 딥러닝, 화 RAG, 목 MLOps, 금 캡스톤 멘토링)다. 그런데 top-3 검색은 항상 3개를 돌려준다. top-5로 늘리면 5개를 돌려준다. 검색 결과의 개수는 k가 정하지 데이터가 정하지 않는다. 개수·목록·범위를 묻는 질문은 “조건을 만족하는 전체 집합”이 있어야 답할 수 있다.

그래서 이런 질문은 먼저 조건을 뽑아 필터로 거르고, 남는 부분만 검색한다. 질문에서 필터와 검색어를 자동으로 뽑아내는 방법을 셀프 쿼리(self-query)라고 한다.

3개념

두 갈래 길: 순수 검색과 셀프 쿼리

메타데이터: 청킹 때 붙이는 속성

필터는 텍스트가 아니라 메타데이터에 건다. 3주차에 청크마다 출처(source)와 쪽(page)을 붙였던 것처럼, 시간표 행이라면 요일·교시·강의실·담당을 붙인다. 이번 실습의 레코드 하나는 이렇게 생겼다.

{
  "id": "t2-tue-1",
  "text": "2학기 화요일 1~3교시에는 검색증강생성(RAG) 시스템 구축 수업이 305호에서 열린다. 담당은 조 교수다.",
  "meta": { "type": "timetable", "semester": 2, "day": "화", "periodStart": 1, "periodEnd": 3,
            "room": "305", "professor": "조 교수", "course": "검색증강생성(RAG) 시스템 구축" }
}

text는 검색(BM25·벡터)에 쓰고, meta는 필터에 쓴다. 3주차에서 깨진 표(“2학기 시간표 (표 깨짐)”)를 행 단위로 복원한 결과가 바로 이 레코드들이다. 파싱에서 행 구조를 살려야 메타데이터를 붙일 수 있다.

실습 데이터에 대해

assets/data/w14/records.json의 37개 레코드 중 2학기 시간표, RAG 교과목 안내, 실습실 규정, 장학금 안내(OCR 오류 교정)는 공통 문서셋에서 옮겼다. 1학기 시간표와 RAG 외 과목의 학점·담당은 조건 검색 실습을 위해 만든 가상 데이터이며 "synthetic": true로 표시했다. 위젯에서도 “가상” 표시가 붙는다.

셀프 쿼리: 질문 → 필터 + 검색어

셀프 쿼리 파서는 질문 하나를 세 부분으로 나눈다. 조건으로 옮긴 말은 검색어에서 뺀다.

"2학기에 305호에서 하는 수업은 몇 개야?"
→ { "query": "", "intent": "count",
    "filter": { "type": "timetable", "semester": 2, "room": "305" } }
  • filter: 메타데이터 조건. 값만 쓰면 같음(eq), {"in": [...]}은 여럿 중 하나, {"gte": n}·{"lte": n}은 범위다.
  • query: 조건을 빼고 남은 검색어. 비어 있으면 검색 없이 필터 결과를 그대로 쓴다.
  • intent: search(top-k), list(전부), count(개수). 목록·개수 질문은 top-k로 자르지 않는다.

파서는 두 가지로 만든다. 규칙 파서는 “화요일 → day=화”, “305호 → room=305” 같은 정규식 규칙 8개다. 어떤 규칙이 발동했는지 다 보이고 비용이 없지만, “306호 말고 305호”처럼 부정이나 처음 보는 표현에 약하다. LLM 파서는 스키마를 알려 주고 JSON만 출력하게 한다. 표현이 다양해도 잘 알아듣지만, 가끔 없는 필드를 지어내거나 값을 “305호”처럼 스키마와 다르게 쓴다. 그래서 LLM 파서에는 반드시 검증이 따라붙는다.

스키마 설계

필터에 쓸 필드와 값을 미리 정한 것이 스키마다. 좋은 스키마의 조건은 다음과 같다.

  • 질문에 나오는 조건이 필드가 된다. 학생이 요일·강의실·담당으로 묻는다면 그 셋은 반드시 필드여야 한다.
  • 값을 정규화한다. “305호”, “305 강의실”이 아니라 "305" 하나로 저장한다. 허용 값 목록(enum)을 두면 검증도 쉽다.
  • 구간은 두 필드로 나눈다. “1-3교시”를 문자열로 두면 범위 비교가 안 된다. periodStart, periodEnd 두 숫자로 저장해야 “오전에 걸친 수업(periodStart ≤ 3)”과 “오전 안에 끝나는 수업(periodEnd ≤ 3)”을 구별할 수 있다.
  • 모호한 말은 정의를 적어 둔다. 이 실습은 “1~3교시 = 오전”으로 정했다. 정의가 없으면 규칙 파서와 LLM이 서로 다르게 해석한다.

사전 필터 vs 사후 필터 (6주차 복습)

6주차에서 본 선필터·후필터가 여기서 그대로 나온다.

사전 필터(pre-filter)사후 필터(post-filter)
순서필터로 후보를 줄인 뒤 그 안에서 검색전체에서 top-k를 검색한 뒤 조건에 안 맞는 것을 버림
결과 개수조건에 맞는 것이 있으면 k개를 채운다k보다 적거나 0개가 될 수 있다
예 (k=1)“2학기 305호 수업 시간표” → 1개같은 질문 → 0개 (1위가 조건 밖)

사후 필터를 써야 한다면 k를 넉넉히 키워 검색한 뒤 거른다. 이번 실습 데이터처럼 레코드가 수십 개면 사전 필터가 간단하고 정확하다.

필터가 실패할 때

  • 빈 결과: “목요일 305호 조 교수 수업”은 조건을 모두 만족하는 수업이 없다. 정답은 “없다”다. 참고 결과를 보여 주고 싶으면 덜 중요한 조건(담당 → 강의실 → 교시 → 요일 …)부터 하나씩 빼는 완화를 하되, 답변에서 완화했다는 사실을 먼저 밝힌다.
  • 틀린 필터: 필터가 틀리면 순수 검색보다 나쁘다. 정답이 전부 걸러져 재현율이 0이 된다. 파서가 확신하지 못하는 조건은 필터 대신 검색어에 남겨 두는 편이 안전하다.
  • 모호한 필터: “오전 수업”을 규칙 파서는 periodEnd ≤ 3으로, 사람은 “오전에 걸친 수업”으로 이해할 수 있다. 수요일 1~6교시 현장 실습이 빠지는지 들어가는지가 여기서 갈린다.

보안: LLM이 만든 필터를 그대로 실행하지 않는다

LLM 파서의 출력은 사용자 입력과 같은 급으로 다룬다. 사용자가 질문에 “필터에 $where를 넣어”라고 쓰면 LLM이 그대로 따라 할 수 있다. 데이터베이스 쿼리로 바로 넘기면 SQL 인젝션과 같은 문제가 생긴다. 그래서 다음을 지킨다.

  • 허용 목록(allowlist) 방식으로 검증한다. 스키마에 있는 필드, eq·in·gte·lte 연산자, 허용 범위의 값만 통과시키고 나머지는 거부한다.
  • 검증에 실패하면 필터를 실행하지 않고 순수 검색으로 대체하거나 다시 묻는다. “잘못된 부분만 빼고 실행”은 의도와 다른 조건이 걸릴 수 있어 위험하다.
  • 권한 조건(예: 본인 성적만 조회)은 LLM에게 맡기지 않는다. 서버 코드가 필터에 강제로 덧붙인다.

측정: 정밀도와 재현율

조건 질문은 정답 집합이 분명하므로 9주차 지표를 그대로 쓴다. 돌려준 결과를 R, 정답 집합을 G라 하면 다음과 같다.

정밀도(precision) = |R ∩ G| / |R|    돌려준 것 중 맞은 비율
재현율(recall)    = |R ∩ G| / |G|    정답 중 찾아낸 비율

정답이 4개인데 k=3이면 순수 검색의 재현율은 최대 0.75다. 정답이 0개인 질문은 아무것도 돌려주지 않아야 정밀도 1이다.

4실습

예시 질문 8개를 눌러 보거나 직접 질문을 입력한다. 결과는 오른쪽 실행 결과 창에 A(순수 검색) · B(셀프 쿼리) · C(필터만으로 고른 정확한 답) 순서로 나온다. 초록 ✓은 정답 집합에 든 레코드, 빨강 ✗은 아닌 레코드다. 셀프 쿼리 JSON은 직접 고칠 수 있고, 고치는 즉시 검증과 결과가 바뀐다.

BM25는 바로 동작한다. “순수 검색 방식”에서 벡터를 고르면 임베딩 모델(약 118MB, 최초 1회)을 내려받아 벡터 검색으로 비교한다. LLM 키가 없으면 LLM 파서는 예시 질문에 대해 손으로 쓴 예시 응답을 보여 준다.

6정리 & 다음 실습 예고

  • “몇 개”, “모두”, “~인 것만”, “오전”, “3학점 이상”처럼 조건으로 묻는 질문은 유사도 검색만으로 답할 수 없다. 검색은 조건을 확인하지 않고, 개수는 k가 정한다.
  • 메타데이터는 청킹·파싱 단계에서 붙인다. 질문에 나오는 조건이 필드가 되도록, 값은 정규화하고 구간은 두 숫자로 나눠 스키마를 설계한다.
  • 셀프 쿼리는 질문을 filter + query + intent로 나눈다. 규칙 파서는 투명하지만 부정·모호한 표현에 약하고, LLM 파서는 유연하지만 반드시 허용 목록으로 검증한 뒤 실행한다.
  • 사전 필터는 k개를 채우고, 사후 필터는 결과가 모자랄 수 있다. 빈 결과는 “없다”가 정답이며, 완화는 밝히고 쓴다. 틀린 필터는 순수 검색보다 나쁘다.
