2왜 필요한가

가장 단순한 검색은 질의 벡터를 저장된 모든 벡터와 하나씩 비교해 점수가 높은 순서로 자르는 것이다. 우리 문서셋은 12개 문서, 청크로 잘라도 수십 개라서 이 방법으로 충분하다. 문제는 규모가 커질 때다.

전부 비교하면 문서 수에 비례해 느려진다

청크 100만 개, 384차원 임베딩이라면 질의 한 번에 곱셈·덧셈이 100만 × 384 = 3억 8,400만 번이다. 이번 주 Challenge C2의 JavaScript 코드로 재면 128차원·1만 개에 약 2ms가 걸리므로, 같은 비율로 늘리면 질의 한 번에 0.6초 안팎이다. 동시 사용자가 10명이면 서버는 이것만 하다가 멈춘다.

두 번째 문제는 “벡터만 저장하면 쓸 데가 없다”는 것이다. 가장 가까운 벡터가 4,821번이라는 것을 알아도, 그 번호에 해당하는 원문이 없으면 LLM에 넘길 컨텍스트를 만들 수 없고, 출처(문서 제목, 쪽)가 없으면 인용을 달 수 없다. “2026학년도 안내 문서에서만 찾아라” 같은 조건도 걸 수 없다.

그래서 벡터스토어는 두 가지를 한다. 벡터와 함께 원문과 메타데이터를 보관하고, 인덱스로 전부 비교하지 않고도 가까운 벡터를 찾는다. 공통 문서셋의 「벡터 데이터베이스와 인덱스」 문서(골든셋 q09)에 적힌 대로, 이 속도에는 대가가 있다. 가끔 가장 가까운 이웃을 놓친다. 이번 주는 그 대가를 숫자로 잰다.

3개념

벡터스토어의 한 행

Flat 인덱스: 정확하지만 O(N)

Flat 인덱스는 인덱스라기보다 “그냥 배열”이다. 벡터를 단위 길이로 정규화해 두면 코사인 유사도는 내적과 같으므로(5주차), 질의마다 N개 벡터와 내적을 구하고 상위 k개를 남긴다. 결과는 항상 정확하다. 비용은 질의 한 번에 N × d번의 곱셈이고, N이 두 배가 되면 시간도 두 배가 된다.

규모질의당 곱셈 수 (d=384)판단
우리 문서셋 청크 수십 개수만 번Flat으로 충분하다
1만 개384만 번Flat으로 수 ms, 대부분 충분하다
100만 개3억 8,400만 번근사 인덱스가 필요하다

근사 최근접 이웃(ANN)과 Recall@k

근사 최근접 이웃(Approximate Nearest Neighbor, ANN) 검색은 “정답 top-k를 거의 다 찾되 훨씬 적게 비교한다”를 목표로 한다. 얼마나 “거의”인지는 Flat의 정확한 결과를 정답으로 놓고 재는데, 이것이 Recall@k다.

Recall@k = |ANN이 돌려준 top-k ∩ Flat의 정확한 top-k| / k
예) 정답 10개 중 9개를 찾았다 → Recall@10 = 0.9

9주차에는 같은 이름의 지표를 “골든셋 정답 문서를 찾았는가”로 쓴다. 이번 주의 Recall@k는 그보다 앞 단계, 즉 “인덱스가 정확한 검색 결과를 얼마나 재현하는가”다. 인덱스가 놓친 청크는 뒤 단계에서 되살릴 수 없다.

HNSW: 층이 있는 그래프를 따라 내려간다

HNSW는 벡터 하나를 노드 하나로 보고, 가까운 벡터끼리 간선으로 잇는다. 모든 노드는 맨 아래층 L0에 있고, 무작위로 뽑힌 일부만 위층에도 올라간다(한 층 올라갈 때마다 대략 1/M로 줄어든다). 검색은 맨 위층 진입점에서 시작해 “이웃 중 질의에 더 가까운 노드”로 옮겨 가다 더 가까워지지 않으면 한 층 내려간다. L0에서는 후보를 efSearch개까지 들고 넓게 살펴본 뒤 상위 k개를 돌려준다.

노드마다 이웃이 수십 개뿐이므로 질의 한 번에 거리 계산이 N번이 아니라 수백 번이면 끝난다. 대신 그래프가 가리키는 방향만 보므로, 진짜 최근접 이웃이 탐색 경로 밖에 있으면 놓친다.

파라미터뜻키우면너무 작으면
M노드당 이웃 수 (L0는 2M)Recall↑, 메모리·구축 시간↑그래프가 성겨 탐색이 막힌다
efConstruction구축할 때 이웃 후보를 찾는 탐색 폭그래프 품질↑, 구축 시간↑엉뚱한 이웃이 연결된다
efSearch검색할 때 들고 다니는 후보 수Recall↑, 질의 시간↑첫 번째 막다른 곳에서 멈춘다

efSearch는 구축이 끝난 뒤에도 질의마다 바꿀 수 있다. 그래서 실무에서는 M과 efConstruction을 넉넉히 잡아 한 번 구축하고, efSearch로 속도와 Recall을 조절한다.

IVF와 PQ: 다른 두 가지 근사

방법아이디어조절 값잃는 것
IVF (Inverted File)k-평균으로 벡터를 nlist개 묶음으로 나누고, 질의와 가까운 nprobe개 묶음만 뒤진다nlist, nprobe묶음 경계 근처의 이웃
PQ (Product Quantization)벡터를 m조각으로 나눠 각 조각을 대표값 256개 중 하나의 번호(1바이트)로 저장한다. 384차원 float32 1,536바이트 → m=48이면 48바이트m, 비트 수거리 계산이 근사가 된다

HNSW는 속도가, PQ는 메모리가 문제일 때 쓴다. 수억 개 규모에서는 IVF와 PQ를 합친 인덱스(FAISS의 IVFPQ)를 많이 쓴다.

메타데이터 필터

“guide 문서에서만 찾아라” 같은 조건을 거는 방법은 두 가지다.

  • 후필터(post-filter): 먼저 top-k를 검색하고 조건에 안 맞는 것을 버린다. 빠르지만 top-k가 전부 조건 밖이면 결과가 0개가 된다.
  • 선필터(pre-filter): 조건에 맞는 항목만 대상으로 검색한다. 항상 k개를 채우지만, 근사 인덱스와 섞으면 구현이 어렵다. 조건에 맞는 노드가 드문드문하면 그래프 탐색이 끊긴다.
k개를 요청했는데 1개가 나온다

Challenge C5에서 “평가 지표” 질의에 type = guide 조건을 후필터로 걸면 top-3 중 조건을 통과하는 것이 1개뿐이다. 필터가 자주 쓰이는 서비스라면 탐색 중에 필터를 적용하는 제품을 고르거나, 후필터라면 k를 넉넉히 키워 검색한다.

4실습

아래 위젯은 시드를 고정한 무작위 단위 벡터 N개와 질의 100개를 만들고, 같은 질의를 Flat(전부 비교)과 HNSW(위젯 안에 순수 JavaScript로 구현)로 검색한다. HNSW의 결과를 Flat의 정확한 top-10과 비교해 Recall@10을 구한다. 벡터는 기본값으로 “주제 군집 20개” 주변에 모이게 만드는데, 실제 문서 임베딩이 주제별로 뭉치는 것을 흉내 낸 것이다. 결과는 오른쪽 실행 결과 창에 나온다.

  • 설정을 바꾸면 자동으로 다시 측정한다. efSearch만 바꾸면 그래프를 다시 만들지 않으므로 바로 나온다. N이 크면 구축에 수 초가 걸리고, 진행률 막대 옆 ■ 취소로 멈출 수 있다.
  • 본전 질의 수는 “구축에 쓴 시간을 질의마다 아낀 시간으로 갚으려면 질의가 몇 번 필요한가”다. Flat은 구축 비용이 없다.
  • efSearch가 k(10)보다 작으면 이 위젯은 탐색하며 거리를 잰 노드 중 가까운 10개를 돌려준다. FAISS와 hnswlib은 이런 경우 efSearch를 k로 올려 버린다.
  • 시간은 브라우저와 컴퓨터마다 다르고 측정할 때마다 조금씩 흔들린다. Recall과 “질의당 거리 계산” 수는 같은 설정이면 항상 같다.

C1. 타입 배열로 Flat top-k 만들기★

벡터 2,000개(64차원)를 Float32Array 하나에 이어 붙여 저장했다. 전부 정렬하지 않고, 크기 k짜리 정렬된 배열에 끼워 넣는 방식으로 top-k를 구하는 topK를 완성한다. 전체 정렬은 N log N이지만 이 방법은 N × k 이하다.

// 시드가 고정된 난수 → 누가 실행해도 같은 벡터
function rng(seed) {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = Math.imul(a ^ (a >>> 15), a | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function randomUnit(n, dim, seed) {
  const r = rng(seed);
  const out = new Float32Array(n * dim); // n개 벡터를 한 줄로 이어 붙임: i번 벡터 = out[i*dim … i*dim+dim-1]
  for (let i = 0; i < n; i++) {
    let s = 0;
    for (let j = 0; j < dim; j++) { const x = r() * 2 - 1; out[i * dim + j] = x; s += x * x; }
    for (let j = 0; j < dim; j++) out[i * dim + j] /= Math.sqrt(s);
  }
  return out;
}

const N = 2000, DIM = 64;
const data = randomUnit(N, DIM, 1);
const query = randomUnit(1, DIM, 2);

function topK(data, dim, q, k) {
  const n = data.length / dim;
  const ids = new Int32Array(k).fill(-1);
  const scores = new Float32Array(k).fill(-Infinity); // 내림차순 유지
  for (let i = 0; i < n; i++) {
    // TODO 1: i번 벡터와 q의 내적 s를 계산한다 (단위 벡터이므로 내적 = 코사인 유사도)
    // TODO 2: s가 현재 k등(scores[k-1])보다 크면, 정렬이 유지되도록 끼워 넣는다
  }
  return { ids: Array.from(ids), scores: Array.from(scores, (x) => +x.toFixed(4)) };
}

C2. N에 따른 검색 시간 재기★

N을 1,000부터 32,000까지 두 배씩 늘리며 Flat 검색의 질의당 평균 시간을 잰다. “1만 개당 ms”가 거의 일정하면 시간이 N에 정비례한다는 뜻이다. 표를 보고 100만 개일 때를 외삽한다.

function rng(seed) {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = Math.imul(a ^ (a >>> 15), a | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
const r = rng(7);
const DIM = 128, K = 10, QUERIES = 20;
const MAX_N = 32000;
const data = Float32Array.from({ length: MAX_N * DIM }, () => r() * 2 - 1);
const queries = Float32Array.from({ length: QUERIES * DIM }, () => r() * 2 - 1);

// 앞에서부터 n개 벡터만 대상으로 하는 Flat top-k (완성된 코드)
function topK(n, qo) {
  const ids = new Int32Array(K).fill(-1);
  const sc = new Float32Array(K).fill(-Infinity);
  for (let i = 0; i < n; i++) {
    let s = 0;
    for (let j = 0; j < DIM; j++) s += data[i * DIM + j] * queries[qo + j];
    if (s <= sc[K - 1]) continue;
    let p = K - 1;
    while (p > 0 && sc[p - 1] < s) { sc[p] = sc[p - 1]; ids[p] = ids[p - 1]; p--; }
    sc[p] = s; ids[p] = i;
  }
  return ids;
}

}

6정리 & 다음 주 예고

  • 벡터스토어는 벡터·원문·메타데이터를 함께 저장한다. 벡터는 찾는 데, 원문은 답하고 인용하는 데, 메타데이터는 거르는 데 쓴다.
  • Flat은 항상 정확하지만 질의 시간이 N에 비례한다. 수만 개 이하라면 Flat이 가장 단순하고 확실한 선택이다.
  • HNSW는 계층 그래프를 따라 내려가며 수백 번의 거리 계산으로 이웃을 찾는다. M·efSearch가 작으면 진짜 이웃을 놓치고, N이 작으면 빠르지도 않다.
  • 인덱스는 Recall@k(정확한 top-k를 얼마나 재현하는가)와 속도를 함께 재서 고른다. 필터가 필요하면 후필터가 결과를 비울 수 있다는 점을 확인한다.

다음 주(7주차 최소 RAG 완성)에는 지금까지 만든 부품(파싱 → 청킹 → 임베딩 → 벡터스토어)을 이어 붙이고, 검색한 청크를 LLM에 넘겨 실제로 답변을 생성한다. 7주차 실습에는 LLM API 키가 필요하다.
