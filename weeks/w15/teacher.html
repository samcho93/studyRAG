T 키로 타이머를 시작한다. LLM 키는 선택이다. 키가 없어도 규칙 기반 생성과 실패 예시로 수업 전체가 진행된다.

오늘 할 수 있게 되는 것

  1. 검색한 청크만 근거로 문항을 만들고, 청크 id + 근거 문장을 인용하게 한다
  2. 출력을 JSON 스키마로 검사하고, 정답·인용·오답을 자동 검증한다
  3. 자동 검증의 한계를 알고, 교사 검토와 윤리를 넣어 파이프라인을 설계한다

“RAG = 챗봇”이라는 고정관념을 깨는 시간이라고 먼저 말한다. 오늘의 산출물은 퀴즈 자체보다 검증기다.

“청킹 퀴즈 5문제 만들어 줘”

예시 응답 · 수업용 작성 예시

Q. 실무에서 오버랩은 보통 청크 크기의 몇 %? → 50%

Q. 재귀 분할의 기준은? → 의미 유사도

문서에는: “청크 크기의 10~20%” · “문단, 줄바꿈, 문장, 공백 순서로”

출처가 없다 → 교사가 한 문항씩 교재를 뒤져야 한다

발문: “이 두 문항, 맞는지 어떻게 확인하나?” 학생이 교재를 찾아보게 1분 준다.

이 예시는 실제 모델 호출 기록이 아니라 수업용으로 작성한 것이라고 분명히 말한다. 요점은 “근거 없이 만들면 확인 비용이 전부 사람에게 간다”는 것.

틀린 답보다 틀린 문제가 더 오래 남는다

  • 학생은 틀린 정답을 외운다
  • 평가에 쓰이면 점수가 틀어진다
  • 응용 1~2: 검색한 청크로 답을 만들었다 → 오늘: 같은 청크로 문제를 만든다
쓰임근거로 검사하는 것
질의응답 (응용 1)답변 문장 ↔ 인용 청크
조건 검색 (응용 2)결과 ↔ 메타데이터 조건
퀴즈 생성 (응용 3)정답 ⊂ 인용 문장, 오답 ⊄ 인용 문장

RAG는 “근거 기반 생성” 전반에 쓰인다. 요약, 카드, 보고서 초안도 같은 구조다. 달라지는 것은 출력 모양과 검사 방법뿐이다.

생성 → 검증 파이프라인

초록 점선을 짚는다: 생성에 준 청크가 곧 검증 기준이다. 근거를 안 주면 검증할 기준도 없다.

④가 사람인 이유는 슬라이드 8에서 다룬다. 지금은 “자동 검증 = 사람이 볼 문항을 줄이는 필터”라고만 말한다.

구조화 출력: JSON 스키마

{ "items": [{
  "type": "mcq",
  "question": "…",
  "answer": "10~20%",
  "choices": ["1~2%", "10~20%", …],
  "citation": {
    "chunk": "rag-chunking#2",
    "quote": "실무에서는 청크 크기의 10~20%를 …"
  }
}] }
  1. 파싱 — 펜스·앞뒤 설명 제거 후 JSON.parse
  2. 스키마 — 필드·타입·선택지 3~5개·정답 포함
  3. 내용 — 인용과 정답이 근거와 맞는가

LLM의 흔한 실수: ```json 펜스, “다음은 퀴즈다”, 끝 쉼표, 필드 누락

“사람이 읽는 문단은 코드가 검사할 수 없다. 필드가 있어야 필드별 규칙을 건다.” 구조화 출력(structured output)이라는 용어를 한 번 소개한다.

공급자별 JSON 모드/스키마 강제 기능이 있지만 이 사이트는 공급자 공통으로 프롬프트 + 검증 방식을 쓴다. JSON 모드를 써도 내용 검증은 여전히 필요하다고 강조한다.

인용 강제와 자동 검증 규칙

인용 = 청크 id + 청크에서 글자 그대로 복사한 문장

규칙잡는 실수
인용 청크 ∈ 근거로 준 청크없는/검색 안 된 청크
인용 문장 ⊂ 그 청크지어낸 문장, 엉뚱한 청크
정답 ⊂ 인용 문장정답 환각
오답 ⊄ 인용 문장 (정답 제외)정답이 둘
bigram 자카드 ≥ 0.7중복 문항
문서 유형·“5O%” 패턴깨진 문서

“글자 그대로”여야 문자열 비교로 검사할 수 있다. 11주차 인용 하이라이트와 같은 원리다.

숫자 비교 주의: “2시간”은 “12시간” 안에 문자열로 들어 있다. 위젯은 숫자 앞뒤에 다른 숫자가 붙지 않도록 검사한다. Challenge C3에서 학생이 단순 includes로 풀면 이 함정을 토론거리로 쓴다.

검증 통과 ≠ 좋은 문제

  • “____ 크기에는 정답이 없다.” (정답: 청크) → 모든 규칙 통과, 그러나 사소한 빈칸
  • 숫자가 나열된 문장: 오답 “30%”가 문장에 있으면 과잉 경고
  • 어순을 바꾼 중복: 자카드 0.45 → 못 잡음
J(A, B) = |A ∩ B| / |A ∪ B|     (두 글자 조각 집합)
"…성적에서 팀 프로젝트가…" vs "…성적 중 팀 프로젝트가…"  → 0.79

규칙은 “근거와 모순되지 않는다”만 보장한다 → 마지막은 사람

발문: “검증기를 더 똑똑하게 만들면 교사 검토를 없앨 수 있나?” LLM으로 검증(LLM-as-judge)하자는 답이 나오면: 그것도 또 하나의 생성이라 검증이 필요하다. 교육 현장에서는 책임 소재 때문에 사람 승인이 남는다.

데모 · RAG 퀴즈 생성기

시연 순서 (검증 결과와 근거 청크는 오른쪽 실행 결과 창)

  1. 처음 화면: 주제 “청킹”, 규칙 기반, 5문항 모두 초록. 결과 창에서 인용 문장이 하이라이트된 것을 보여 준다. 오답(재귀 분할, 청킹 등)은 같은 “청킹” 분류 용어에서 왔다.
  2. “실습실 규정” → 검색 1·2위가 FAQ(broken-mixed) 중복 문단 → Q1·Q2 같은 문항, 경고(유사도 1.00, 깨진 문서).
  3. “장학금 (스캔 깨짐)” → Q2 “1O시간”, Q3 “5O%”, Q4 “2l4”가 빨간 실패(OCR 의심). 규칙 생성기는 글자를 그대로 복사하므로 OCR 오류도 복사한다.
  4. 생성 방식 “실패 예시” → Q2 환각(100 vs 60), Q3 정답 둘, Q4 인용 청크 오류(facility-rules#1에 있다), Q5 중복 경고(0.79), Q6 스키마 위반.
  5. 예시 세트 “JSON 형식 오류” → 끝 쉼표 하나로 파싱 실패, 문항 0개.
  6. “퀴즈 풀기”로 풀고 채점 → 실패 문항은 자동 제외. JSON 내려받기로 verify/review 필드를 보여 준다.

키가 있으면 마지막에 “LLM 생성”을 한 번 시연한다. 결과가 매번 다르므로 검증 결과를 학생과 함께 읽는다.

관찰 질문

  1. 초록 문항의 인용 문장을 근거 청크에서 찾는다. 오답은 어디서 왔나?
  2. “실습실 규정”의 중복 문항은 생성기 탓인가, 데이터 탓인가?
  3. 규칙 생성기는 왜 “5O%”를 정답으로 썼나?
  4. 실패 예시 Q2~Q4는 각각 어떤 규칙에 걸렸나? Q5는 왜 경고인가?
  5. JSON 형식 오류: 쉼표 하나로 몇 문항을 잃었나?
  6. 검증은 통과했지만 승인하지 않을 문항을 찾는다

1~4는 짝 활동 15분, 5~6은 휴식 후 전체 토론.

2번 기대 답: 데이터(3주차 파싱) 문제다. 생성기는 받은 청크를 충실히 썼다. 중복 제거는 색인 전에 하는 것이 맞고, 검증기의 중복 검사는 마지막 안전망이다.

6번 기대 답: “____ 크기에는 정답이 없다”, 표 깨짐 문서의 긴 문항, “생성된 수치” 오답이 어색한 문항.

코드로 확인하기 · 정답 ⊂ 근거, 오답 ⊄ 근거

const quote = '한 사람이 연속으로 사용할 수 있는 시간은 최대 12시간이다.';
const items = [
  { answer: '12시간', choices: ['6시간', '12시간', '24시간'] },
  { answer: '24시간', choices: ['12시간', '24시간', '48시간'] },
];
for (const it of items) {
  const inSource = quote.includes(it.answer);
  const rest = quote.split(it.answer).join(' ');
  const alsoCorrect = it.choices.filter((c) => c !== it.answer && rest.includes(c));
  console.log(it.answer, { inSource, alsoCorrect });
}

실행 결과: 12시간 { inSource: true, alsoCorrect: [] }, 24시간 { inSource: false, alsoCorrect: [ '12시간' ] }.

두 번째 문항은 정답을 잘못 고르고(환각), 진짜 정답을 오답 자리에 넣은 경우다. 규칙 두 개가 동시에 걸린다. quote.split(answer)로 정답을 먼저 지우는 이유를 묻는다(오답이 정답의 일부일 때 오탐 방지).

사람 검토와 교육용 활용 윤리

교사 검토에서 보는 것

  • 답이 하나로 정해지는가
  • 학습 목표와 관련 있는가
  • 오답이 그럴듯하되 명백히 틀렸나
  • 깨진 문서 문항은 원본 확인

윤리

  • 저작권 — 원문 권리 확인, 출처 표기
  • 정답 오류 책임 — 배포한 사람이 진다
  • 개인정보 — 학생 정보는 프롬프트 금지

빈칸 문제는 원문 문장을 거의 그대로 옮긴다. 교재·유료 자료를 대량으로 넣어 배포하면 복제가 된다는 점을 짚는다. 이 사이트의 문서셋은 수업용으로 작성한 자료다.

“AI가 만든 문제가 틀렸으면 누구 책임인가?” — 짧게 묻고 답을 듣는다. 결론: 평가에 쓰기 전 검토, 오류 신고 경로, “자동 생성 문항” 표시.

부록 B · C1 정답

const PATTERN = /(?:오전|오후)\s?\d+시(?!간)|\d+(?:~\d+)?%|\d+시간/;

function makeCloze(sentence) {
  const m = sentence.match(PATTERN);
  if (!m) return null;
  return {
    question: sentence.slice(0, m.index) + '____' + sentence.slice(m.index + m[0].length),
    answer: m[0],
  };
}

const samples = [
  '수료 요건은 출석률 80% 이상과 팀 프로젝트 최종 발표 통과다.',
  '한 사람이 연속으로 사용할 수 있는 시간은 최대 12시간이다.',
  '실습실은 수업 시간 외에도 평일 오후 9시까지 개방된다.',
  '청킹은 긴 문서를 검색 단위로 자르는 과정이다.',
];
for (const s of samples) console.log(makeCloze(s));

실행 결과: { question: '수료 요건은 출석률 ____ 이상과 …', answer: '80%' }, '…최대 ____이다.' / '12시간', '…평일 ____까지 개방된다.' / '오후 9시', 마지막 null.

왜: 정답을 원문에서 잘라 오므로 “정답 ⊂ 근거 문장”이 구조적으로 보장된다. 이것이 규칙 기반 생성의 장점이다. 정규식 순서에 주의: \d+시를 먼저 두면 “12시간”의 “12시”가 잡힌다 → (?!간)으로 막는다.

부록 B · C2 정답

const corpus = await (await fetch('/assets/data/corpus/corpus.json')).json();
const PCT = /\d+(?:~\d+)?%/g;

// every percent value in the healthy documents (broken OCR docs would leak "5O%")
const pool = [...new Set(corpus.documents
  .filter((d) => d.type !== 'broken')
  .flatMap((d) => d.text.match(PCT) ?? []))];
console.log('pool:', pool);

const first = (s) => Number(s.match(/\d+/)[0]);

function pickDistractors(answer, sentence, n = 3) {
  return pool
    .filter((v) => v !== answer && !sentence.includes(v)) // never a second correct answer
    .sort((a, b) => Math.abs(first(a) - first(answer)) - Math.abs(first(b) - first(answer)))
    .slice(0, n);
}

function parseReply(text) {
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  const body = fenced ? fenced[1] : text;
  return JSON.parse(body.slice(body.indexOf('{'), body.lastIndexOf('}') + 1));
}

function validate(data) {
  const errors = [];
  const str = (v) => typeof v === 'string' && v.trim() !== '';
  if (!Array.isArray(data?.items)) return ['items: 배열이어야 한다'];
  data.items.forEach((it, i) => {
    const p = `items[${i}]`;
    if (!['mcq', 'short'].includes(it.type)) errors.push(`${p}.type: mcq 또는 short`);
    if (!str(it.question)) errors.push(`${p}.question: 비어 있다`);
    if (!str(it.answer)) errors.push(`${p}.answer: 비어 있다`);
    if (it.type === 'mcq') {
      if (!Array.isArray(it.choices) || it.choices.length < 3 || it.choices.length > 5) errors.push(`${p}.choices: 3~5개여야 한다`);
      else if (!it.choices.includes(it.answer)) errors.push(`${p}.choices: 정답이 선택지에 없다`);
    }
    if (!it.citation) errors.push(`${p}.citation: 없다`);
    else {
      if (!str(it.citation.chunk)) errors.push(`${p}.citation.chunk: 비어 있다`);
      if (!str(it.citation.quote)) errors.push(`${p}.citation.quote: 비어 있다`);
    }
  });
  return errors;
}

function bigrams(s) {
  const t = s.replace(/[\s\p{P}\p{S}_]+/gu, '').toLowerCase();
  const g = new Set();
  for (let i = 0; i < t.length - 1; i++) g.add(t.slice(i, i + 2));
  return g;
}
function jaccard(a, b) {
  const A = bigrams(a), B = bigrams(b);
  let inter = 0;
  for (const x of A) if (B.has(x)) inter++;
  return inter / (A.size + B.size - inter);
}
function dedupe(questions, threshold) {
  const kept = [];
  for (const q of questions) if (!kept.some((k) => jaccard(k, q) >= threshold)) kept.push(q);
  return kept;
}
