근거에서 문제를 만들고, 근거로 검사한다

RAG는 질문에 답하는 데서 끝나지 않는다. 검색한 청크로 퀴즈를 만들고, 만든 문항이 그 청크와 맞는지 코드로 검사한다. PART 5의 마지막 실습이다.

1학습 목표

이번 실습이 끝나면
  • 검색한 청크만 근거로 퀴즈 문항을 만들고, 문항마다 청크 id와 근거 문장을 인용하게 할 수 있다.
  • 생성 결과를 JSON 스키마로 검사하고, 정답·인용·오답 선택지를 자동 검증 규칙으로 확인할 수 있다.
  • 자동 검증이 잡지 못하는 문제를 구분하고, 교사 검토와 교육용 활용 윤리를 반영한 생성 파이프라인을 설계할 수 있다.

2왜 필요한가

교사가 LLM에게 “청킹 단원 복습 퀴즈 5문제를 만들어 줘”라고만 부탁했다고 하자. 근거 문서를 주지 않았으므로 모델은 기억에 의존해 그럴듯한 문항을 만든다.

예시 응답 · 수업용 작성 예시 근거 없이 만든 퀴즈

Q. 실무에서 오버랩은 보통 청크 크기의 몇 %로 두는가? ① 10% ② 30% ③ 50% (정답) ④ 80%

Q. 재귀 분할은 무엇을 기준으로 자르는가? ① 문자 수 ② 의미 유사도 (정답) ③ 토큰 수 ④ 페이지

두 문항 모두 틀렸다. 문서셋의 「청킹 전략」에는 “청크 크기의 10~20%를 오버랩으로 두는 경우가 많다”, 재귀 분할은 “문단, 줄바꿈, 문장, 공백 순서로 구분자를 바꿔 가며 자른다”고 적혀 있다. 그런데 문항에는 출처가 없으므로 교사는 한 문항씩 교재를 뒤져 확인해야 한다. 확인하지 않고 배포하면 학생은 틀린 정답을 외우고, 그 퀴즈가 평가에 쓰이면 점수까지 틀어진다. 틀린 답변 하나보다 틀린 문제 하나가 더 오래 남는다.

응용 1(학과 안내 챗봇)과 응용 2(조건 검색)에서는 검색한 청크로 답을 만들었다. 같은 구조로 문제도 만들 수 있다. 다만 이번에는 두 가지가 더 필요하다.

  • 근거 기반 생성: 검색된 청크만 재료로 쓰고, 문항마다 어느 청크의 어느 문장에서 나왔는지 인용하게 한다.
  • 자동 검증: 인용이 있으니 “정답이 정말 그 문장에 있는가”를 코드로 검사할 수 있다. 사람은 검증을 통과한 문항만 본다.

3개념

생성 → 검증 파이프라인

근거 기반 생성: RAG의 다른 쓰임

지금까지 RAG의 마지막 단계는 “답변 생성”이었다. 그러나 검색한 청크는 무엇을 만들든 재료가 될 수 있다. 달라지는 것은 출력의 모양과, 그 출력을 검사하는 방법이다.

쓰임출력근거로 검사하는 것
질의응답 (응용 1)답변 + 인용 번호답변 문장마다 인용한 청크에 핵심어가 있는가
조건 검색 (응용 2)조건에 맞는 문서 목록결과가 메타데이터 조건을 정말 만족하는가
퀴즈 생성 (응용 3)문항 JSON (질문·정답·선택지·인용)정답이 인용 문장에 있는가, 오답이 정답이 되지 않는가

구조화 출력: JSON 스키마

“퀴즈 5문제를 만들어 줘”의 결과가 사람이 읽는 문단이면 코드로 검사할 수 없다. 출력 형식을 필드가 정해진 JSON으로 고정하면, 필드마다 규칙을 걸 수 있다. 이것을 구조화 출력(structured output)이라 한다. 이번 실습의 스키마는 다음과 같다(// 뒤는 설명이며 실제 JSON에는 주석을 쓸 수 없다).

{
  "items": [
    {
      "type": "mcq",                      // "mcq"(객관식) 또는 "short"(단답형)
      "question": "실무에서 오버랩으로 흔히 두는 비율은?",
      "answer": "10~20%",
      "choices": ["1~2%", "10~20%", "40~50%", "80~90%"],   // mcq만, 3~5개, 정답 포함
      "citation": {
        "chunk": "rag-chunking#2",        // 검색된 청크의 id
        "quote": "실무에서는 청크 크기의 10~20%를 오버랩으로 두는 경우가 많다."
      }
    }
  ]
}

LLM은 이 형식을 자주 조금씩 어긴다. 코드 펜스(```json)로 감싸거나, 앞에 “다음은 퀴즈다” 같은 문장을 붙이거나, 마지막 항목 뒤에 쉼표를 남기거나, 필드를 빠뜨린다. 그래서 검사는 세 단계로 한다.

  1. 파싱: 펜스와 앞뒤 설명은 벗겨 내고 JSON.parse. 실패하면 그 응답의 문항은 하나도 쓸 수 없다.
  2. 스키마 검증: 필드가 있는가, 타입이 맞는가, 선택지가 3~5개이고 정답을 포함하는가.
  3. 내용 검증: 인용과 정답이 근거와 맞는가 (아래 규칙).

인용 강제: 청크 id + 원문 그대로의 문장

문항마다 citation.chunk(검색된 청크의 id)와 citation.quote(그 청크에서 글자 그대로 복사한 문장)를 요구한다. “그대로”가 중요하다. 원문과 같은 문자열이어야 청크 안에 있는지 문자열 비교로 확인할 수 있고, 11주차 인용 하이라이트처럼 원문 위치에 표시할 수도 있다. 모델이 문장을 요약하거나 바꿔 적으면 그것만으로 검증 실패다.

자동 검증 규칙과 한계

규칙잡는 실수검사 방법못 잡는 것
인용 청크 존재없는 청크 id, 검색되지 않은 청크 인용인용 id가 근거로 준 청크 id 집합에 있는가—
인용 문장 존재지어낸 문장, 엉뚱한 청크 인용인용 문장이 그 청크 원문에 포함되는가문장은 맞지만 질문과 관계없는 인용
정답 ⊂ 근거 문장정답 환각 (근거는 60, 정답은 100)정답 문자열이 인용 문장에 있는가 (숫자는 앞뒤 숫자와 붙지 않게)근거에 있지만 질문에 맞지 않는 정답
오답 ⊄ 근거 문장정답이 둘인 선택지정답을 지운 인용 문장에 다른 선택지가 있는가바꿔 말한 정답. 숫자가 나열된 문장에서는 과잉 경고
중복같은·거의 같은 문항두 글자 조각(bigram)의 자카드 유사도(Jaccard similarity) ≥ 0.7어순을 바꾼 바꿔 말하기
깨진 문서OCR “5O%”, 표 깨짐문서 유형, 숫자 속 O·l 패턴패턴에 없는 오류 (예: 3을 8로 읽음)

중복 검사는 이렇게 생각하면 된다. 두 문장을 두 글자씩 잘라 조각 집합을 만들고, 겹치는 조각이 전체 조각 중 얼마인지 본다. “RAG 교과목 성적에서 팀 프로젝트가 차지하는 비율은?”과 “…성적 중 팀 프로젝트가…”는 조각 대부분이 같다. 이 비율을 식으로 쓴 것이 자카드 유사도다.

J(A, B) = |A ∩ B| / |A ∪ B|        A, B = 공백·부호를 지운 문장의 두 글자 조각 집합
"…성적에서 팀 프로젝트가 차지하는 비율은?" vs "…성적 중 팀 프로젝트가 차지하는 비율은?"   → 0.79 (중복)
"…성적에서 팀 프로젝트가…" vs "팀 프로젝트는 RAG 교과목 성적의 몇 %를 차지하나?"        → 0.45 (못 잡음)
검증 통과 ≠ 좋은 문제

자동 검증은 “근거와 모순되지 않는다”만 보장한다. “____ 크기에는 정답이 없다.”(정답: 청크)는 모든 규칙을 통과하지만 학습 목표와 상관없는 사소한 빈칸이다. 정답이 하나로 정해지는지, 수업에서 강조한 내용인지, 난이도가 맞는지는 사람이 판단한다.

사람 검토: 교사 검토 단계

그래서 파이프라인의 마지막은 사람이다. 자동 검증은 사람이 볼 문항 수를 줄이는 필터이고, 최종 승인은 교사가 한다. 검토에서 보는 것은 다음과 같다.

  • 질문만 읽고 답이 하나로 정해지는가 (빈칸 앞뒤 문맥이 충분한가)
  • 이번 단원의 학습 목표와 관련 있는가
  • 오답 선택지가 그럴듯하되 명백히 틀렸는가 (규칙 기반 생성기의 “생성된 수치”는 특히 확인한다)
  • 깨진 문서에서 나온 문항은 원본을 확인했는가

내보낸 JSON에는 문항마다 verify(자동 검증 결과)와 review(approved/pending)가 함께 기록된다. 누가 무엇을 확인했는지 남기는 것이다.

교육용 활용 윤리

저작권

근거 문서를 퀴즈 재료로 써도 되는 권리가 있는지 확인한다. 빈칸 문제는 원문 문장을 거의 그대로 옮기므로, 교재·유료 자료를 대량으로 넣어 배포하면 복제가 된다. 내보낼 때 출처(청크 id, 문서명)를 함께 남긴다.

정답 오류 책임

자동 생성이어도 배포한 사람이 책임진다. 평가(시험·성적)에 쓰기 전에는 반드시 검토하고, 학생이 오류를 신고할 경로를 둔다. “자동 생성 문항”이라고 표시한다.

개인정보

학생 이름, 성적, 상담 기록을 프롬프트에 넣지 않는다. 외부 LLM API로 전송되기 때문이다. API 키는 이 사이트처럼 탭 안(sessionStorage)에만 둔다.

4실습

아래 위젯은 문서셋을 재귀 분할(200자)로 청킹하고 BM25로 상위 k개 청크를 찾은 뒤, 그 청크만으로 문항을 만든다. 키가 없으면 규칙 기반 생성(키 없이)이 동작한다. 근거 문장에서 숫자(%, 시간, 시각, 학기 등)나 기술 용어를 빈칸으로 바꾸고, 문서셋에서 같은 종류의 다른 값을 골라 오답으로 쓴다. 모델을 쓰지 않으므로 모든 과정이 코드로 보인다. 검증 결과와 근거 청크(인용한 문장 하이라이트)는 오른쪽 실행 결과 창에 나온다.

“하이브리드” 검색을 고르면 임베딩 모델(약 118MB, 최초 1회)을 내려받아 BM25와 벡터 검색을 RRF로 합친다. API 키를 입력하면 같은 근거 청크와 JSON 스키마로 LLM에게 문항을 요청할 수 있다. 키는 이 탭의 sessionStorage에만 저장된다.

관찰 질문

  1. 처음 화면(주제 “청킹”, 규칙 기반, 보통)에서 모든 문항이 초록이다. 문항 하나를 골라 결과 창의 근거 청크에서 인용 문장을 찾는다. 오답 선택지는 어디에서 왔나?
  2. 주제를 실습실 규정으로 바꾼다. 검색 1·2위는 어떤 문서인가? Q1과 Q2가 왜 같은 문항이 되었나? 이것은 생성기의 문제인가, 데이터(3주차 파싱)의 문제인가?
  3. 주제를 장학금 (스캔 깨짐)으로 바꾼다. 빨간 문항의 정답은 무엇인가? 규칙 생성기는 왜 “5O%”를 그대로 정답으로 썼나? 검증기가 없었다면 학생은 무엇을 외웠을까?
  4. 생성 방식을 실패 예시로 바꾼다. Q2·Q3·Q4는 각각 어떤 규칙에 걸렸나? Q5는 왜 실패가 아니라 경고인가? Q1의 근거 문장에는 30%·20%·10%도 있다. 오답에 30%를 넣으면 검증기는 어떻게 판정할까? 그 판정은 옳은가?
  5. 예시 세트를 JSON 형식 오류로 바꾼다. 결과 창의 “모델 원문 출력”에서 파싱이 실패한 위치를 찾는다. 쉼표 하나 때문에 몇 문항을 잃었나?
  6. 퀴즈 풀기로 바꿔 직접 풀고 채점한다. 검증에 실패한 문항은 왜 빠졌나? 몇 문항을 승인한 뒤 JSON으로 내보내고 review, verify 필드를 확인한다.
  7. 난이도를 어려움(단답형)으로 바꾸고 “____ 크기에는 정답이 없다.” 같은 문항을 찾는다. 검증은 통과했지만 교사라면 승인하겠는가? (키가 있으면 LLM 생성 결과와 문항의 자연스러움, 검증 실패 수를 비교한다.)

5Challenge

난이도 순서다. 코드 상자는 직접 고칠 수 있고, ▶ 실행(또는 Ctrl+Enter)을 누르면 결과가 오른쪽 실행 결과 창에 나온다(휴대폰에서는 코드 바로 아래). 코드는 워커에서 돌아가며 10초가 지나면 자동으로 멈춘다. 모델도 LLM API도 쓰지 않는다. LLM 출력이 필요한 곳은 가짜 함수(mockLLM)가 대신한다.

C1. 문장 하나로 빈칸 문제 만들기★

근거 문장에서 “숫자+%”, “숫자+시간”, “오전/오후 N시” 중 처음 나오는 것을 찾아 빈칸(____)으로 바꾸는 makeCloze를 작성한다. 찾지 못하면 null을 돌려준다. 정답은 원문에서 잘라 온 문자열이므로 “정답이 근거 문장에 있다”는 검증을 자동으로 통과한다.

function makeCloze(sentence) {

  // TODO: 찾으면 그 부분을 '____'로 바꾼 question과 answer를 돌려준다
  // TODO: 못 찾으면 null을 돌려준다

6정리 & PART 5 마무리

  • RAG는 질의응답만이 아니라 근거 기반 생성에 쓰인다. 검색한 청크가 생성의 재료이자 검증의 기준이다.
  • 출력을 JSON 스키마로 고정하고 문항마다 청크 id와 원문 그대로의 문장을 인용하게 하면, 파싱 → 스키마 → 내용 순서로 코드가 검사할 수 있다.
  • 자동 검증은 정답 환각, 정답이 둘인 선택지, 엉뚱한 인용, 중복, 깨진 문서를 잡는다. 그러나 “좋은 문제인가”는 잡지 못한다. 마지막 승인은 교사가 한다.
  • 교육용으로 쓸 때는 저작권, 정답 오류 책임, 개인정보를 함께 설계한다.

팀 프로젝트로 잇기

  • 팀 프로젝트의 질의응답 서비스에 생성 → 검증 단계를 하나 더한다. 답변의 인용을 이번 실습의 규칙(인용 문장 존재, 핵심 값 포함)으로 검사해 보고서에 검증 통과율을 적는다.
  • 퀴즈 생성기로 팀 문서의 골든셋 초안을 만든다. 문항의 question·answer·citation.quote는 골든셋의 질문·정답·근거와 같은 모양이다. 교사(또는 팀원)가 승인한 문항만 골든셋에 넣고, 12주차 팀 결과 보드와 같은 형식으로 Recall@k를 측정한다.
  • 발표에서는 평균 점수와 함께 검증기가 잡은 실패 사례 하나를 보여 준다. 실패를 보여 주는 팀이 시스템을 더 잘 안다.
