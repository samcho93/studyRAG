1학습 목표

이번 주가 끝나면
  • 코사인 유사도·내적·유클리드 거리의 차이와, 정규화하면 셋의 순위가 같아지는 이유를 설명할 수 있다.
  • 임베딩 모델(다국어/영어 전용)과 e5 접두어가 한국어 검색 결과를 어떻게 바꾸는지 관찰하고 근거를 들어 모델을 고를 수 있다.
  • 유사도 행렬, top-k 순위, 2D 주성분 투영을 직접 구현할 수 있다.

2왜 필요한가

학생이 “랩실에서 커피 마셔도 돼?”라고 묻는다. 실습실 이용 규정에는 답이 분명히 있다. “실습실 안에서는 음료를 포함한 모든 음식물 섭취가 금지된다.” 그런데 질문과 규정 문장이 공유하는 단어는 거의 없다. 랩실과 실습실, 커피 마셔도와 음식물 섭취는 글자가 다르다.

글자가 다르면 찾지 못한다

단어가 겹치는 정도로만 문서를 고르면 이 질문의 정답 문장은 순위 밖으로 밀리기 쉽다. 반대로 “성적 우수 장학금은 평점 4.0 이상인 학생에게 지급하지 않는다”처럼 단어는 거의 같고 뜻은 반대인 문장은 높은 점수를 받는다.

필요한 것은 뜻이 가까우면 가까운 숫자가 나오는 표현이다. 그것이 임베딩(embedding)이다. 그러나 임베딩도 만능이 아니다. 한국어를 배우지 않은 모델을 쓰면 모든 문장이 비슷하다고 판단해 검색이 통째로 무너진다. 이번 주 실습에서 두 경우를 모두 확인한다.

3개념

임베딩: 문장을 방향으로 바꾼다

임베딩 모델은 문장을 고정 길이의 실수 벡터로 바꾼다. 학습 과정에서 뜻이 가까운 문장 쌍은 가까운 방향을, 관련 없는 쌍은 먼 방향을 갖도록 조정된다. 그래서 “랩실”과 “실습실”처럼 글자는 달라도 비슷하게 쓰이는 표현은 비슷한 방향으로 간다. 검색 시스템은 질문도 같은 모델로 벡터로 바꾼 뒤, 가장 가까운 청크 벡터를 고른다.

가까움을 재는 세 가지 방법

척도식무엇을 보나주의
코사인 유사도(cosine similarity)a·b / (‖a‖‖b‖)두 벡터 사이 각도. −1~1, 클수록 비슷길이를 무시한다
내적(dot product)Σ aᵢbᵢ방향 × 길이길이가 긴 벡터가 부당하게 유리하다
유클리드 거리(Euclidean distance)‖a − b‖끝점 사이 직선 거리. 작을수록 비슷길이가 다르면 방향이 같아도 멀다

세 척도는 벡터를 정규화(길이를 1로 맞춤)하면 하나로 모인다. 길이가 1이면 분모가 1이므로 코사인 = 내적이고, 유클리드 거리도 코사인만의 함수가 된다.

‖a‖ = ‖b‖ = 1 이면
  cos(a, b) = a · b
  ‖a − b‖² = ‖a‖² + ‖b‖² − 2 a·b = 2 − 2 cos(a, b)

그래서 정규화된 벡터에서는 어떤 척도로 정렬해도 순위가 같다. 이 과정의 embed.js는 모델 출력을 정규화해서 돌려주고, vectorstore.js도 저장할 때 다시 정규화한다. 덕분에 검색은 가장 빠른 연산인 내적 한 번으로 끝난다.

e5 모델의 접두어: query: 와 passage:

이번 주 기본 모델 multilingual-e5-small은 학습할 때 질문 앞에 query: , 문서 앞에 passage: 를 붙였다. 사용할 때도 똑같이 붙여야 학습 때와 같은 조건이 된다. 모델 카드는 문장끼리 비교하는 대칭 작업(유사도 측정, 군집)에는 양쪽 모두 query: 를 쓰라고 안내한다.

// core/embed.js가 모델 정보에 따라 접두어를 자동으로 붙인다
await embedBatch(chunks, { role: 'passage' }); // → "passage: 청킹은 …"
await embed('청킹이 뭐야?', { role: 'query' }); // → "query: 청킹이 뭐야?"

실습 위젯의 히트맵(문장 ↔ 문장)은 양쪽에 query: 를, 질의 순위(질의 ↔ 문장)는 질의에 query: , 문장에 passage: 를 붙인다. 접두어를 빠뜨리는 것은 e5 계열에서 가장 흔한 실수다. 오류 없이 돌아가면서 점수만 조용히 나빠지므로 발견하기도 어렵다.

e5 점수는 원래 높게 몰린다

e5 모델 카드는 코사인 점수가 대체로 0.7~1.0 근처에 몰리는 것이 정상이라고 설명한다(학습에 낮은 온도 값을 썼기 때문이다). 그래서 “0.8이면 관련 있음” 같은 절대 기준은 모델마다 다르다. 검색에서 중요한 것은 값의 크기가 아니라 순위다.

모델 선택: 다국어냐 영어 전용이냐

임베딩 모델은 학습한 언어만 제대로 이해한다. 영어 문장으로만 학습한 all-MiniLM-L6-v2에 한국어를 넣으면 토크나이저가 한글을 의미 있는 조각으로 자르지 못하고, 모든 문장이 비슷한 벡터가 된다. 유사도가 높은 값으로 몰리고 주제가 섞인다. 위젯에서 이 모델을 고르는 것이 이번 주의 핵심 실패 실험이다.

위젯의 모델언어차원이번 주 역할
multilingual-e5-small다국어(한국어 포함)384기본 모델. 접두어 필요

실무에서 쓸 만한 한국어 모델(KURE, BGE-M3, OpenAI text-embedding-3 등)의 크기·라이선스·비용 비교는 이론 페이지 한국어 임베딩 모델 비교에 정리했다.

차원: 크면 좋은가

차원은 벡터 하나에 담긴 숫자의 개수다. 차원이 크면 더 많은 구분을 담을 수 있지만, 저장 공간과 검색 계산량이 차원에 비례해 늘어난다. 32비트 실수 기준으로 384차원 벡터 하나는 1,536바이트, 1024차원은 4,096바이트다. 청크 100만 개면 각각 약 1.5GB와 4.1GB가 된다. 차원이 크다고 한국어를 더 잘하는 것도 아니다. 모델이 무엇으로 학습했는지가 먼저다.

고차원을 눈으로 보기: 주성분 분석

384차원은 그릴 수 없으므로, 위젯은 주성분 분석(PCA, Principal Component Analysis)으로 점들이 가장 넓게 퍼진 두 방향을 찾아 그 위에 투영한다. 방향은 거듭제곱법(power iteration)으로 찾는다. 공분산 행렬을 벡터에 계속 곱하면 벡터가 분산이 가장 큰 방향으로 끌려가는 성질을 쓴다.

1. 모든 벡터에서 평균을 뺀다 (중심화)
2. 임의의 v에서 시작해  v ← normalize(Xᵀ(X v))  를 수렴할 때까지 반복 → PC1
3. PC1 성분을 빼 가며 같은 반복 → PC2
4. 각 점을 (x·PC1, x·PC2)로 그린다

두 축이 설명하는 분산은 전체의 일부뿐이다. 2D 그림에서 가까워 보여도 실제 코사인은 다를 수 있으므로, 그림은 전체 모양을 보는 데만 쓰고 판단은 히트맵 값으로 한다.
