1학습 목표

이번 주가 끝나면
  • 색인 단계와 질의 단계를 구분하고, 각 단계가 만드는 산출물의 모양을 설명할 수 있다.
  • 문서 로드부터 생성까지 이어지는 answer(question) 함수를 작성할 수 있다.
  • 틀린 답의 원인을 검색 → 프롬프트 → 생성 순서로 추적하고, 골든셋으로 hit를 확인할 수 있다.

2왜 필요한가

1주차에 LLM 혼자 “성적 우수 장학금 지급액은?”에 답하게 하면 그럴듯한 숫자를 지어낸다는 것을 봤다. 검색증강생성(RAG)은 관련 문서를 먼저 찾아 LLM 입력에 넣어 이 문제를 줄인다. 4~6주차에 그 부품을 하나씩 만들었다. 이제 조립만 하면 된다.

그런데 조립해서 돌려 보면 이런 일이 생긴다.

“문서에서 찾을 수 없다” — 그런데 답은 문서셋 안에 있다

“RAG 수업은 무슨 요일 몇 교시이고 어느 강의실인가?”라고 물으면 파이프라인은 “제공된 근거 문서에서 요일·교시·강의실은 찾을 수 없다”고 답한다. 정답(화요일 1-3교시, 305호)은 2학기 시간표 문서에 분명히 있다.

질문과 답만 보면 원인을 알 수 없다. 모델이 멍청한가? 프롬프트가 나쁜가? 문서가 검색되지 않았나? 문서 자체가 깨졌나? 파이프라인을 한 덩어리로 돌리면 이 질문에 답할 방법이 없다. 그래서 이번 주는 파이프라인을 만들면서 동시에 각 단계의 산출물을 꺼내 보는 법을 익힌다. 결론부터 말하면 이 사례의 범인은 LLM이 아니라 검색이다.

3개념

두 단계: 색인과 질의

색인(indexing) 단계는 문서를 검색할 수 있는 형태로 바꿔 저장하는 일이다. 문서가 바뀌지 않으면 다시 할 필요가 없다. 질의(query) 단계는 질문이 들어올 때마다 검색하고 답을 만드는 일이다. 색인은 느려도 괜찮지만 질의는 빨라야 한다. 위젯에서 ③ 임베딩이 수백 ms~수 초 걸리는 동안 ④ 검색은 수 ms로 끝나는 것을 직접 확인한다.

두 단계를 잇는 약속이 하나 있다. 질문과 청크를 같은 임베딩 모델로 벡터화해야 한다. 모델이 다르면 두 벡터는 서로 다른 공간에 있어 코사인 유사도가 의미를 잃는다. e5 계열이라면 청크에는 passage: , 질문에는 query: 접두어를 붙이는 것까지 약속에 포함된다(5주차).

각 단계의 산출물 모양

디버깅은 산출물을 꺼내 보는 일이다. 무엇이 나와야 정상인지 먼저 알아 둔다. 숫자는 이번 주 기본 설정(재귀 분할 200자, 오버랩 0, multilingual-e5-small, top-3) 기준이다.

단계입력산출물코드
① 문서 로드corpus.json{ id, title, type, text } × 12fetch
② 청킹문서 원문{ id: 'doc#i', doc, start, end, text } × 37chunk()
③ 임베딩·저장청크 텍스트384차원 벡터 × 37 → { id, vector, meta }embedBatch(), store.add()
④ 검색질문 벡터[{ id, score, meta }] k개, 점수 내림차순store.search(q, k)
⑤ 프롬프트질문 + 청크 k개{ system, messages }, 근거에 [1] [2] 번호ragPrompt()
⑥ 생성프롬프트{ text, usage }generate()

④의 점수는 코사인 유사도다. 벡터스토어가 벡터를 미리 길이 1로 정규화해 두므로 질문 벡터 q와 청크 벡터 c의 점수는 내적 q · c = Σ qᵢcᵢ 하나로 계산된다. 이 점수로 정렬해 앞에서 k개를 자르는 것이 검색의 전부다.

디버깅 순서: 검색부터 확인한다

답이 틀리면 LLM부터 의심하기 쉽다. 하지만 LLM은 ⑤의 프롬프트만 본다. 프롬프트에 근거가 없으면 어떤 모델도 맞힐 수 없다. 그래서 순서를 거꾸로 올라가지 않고, 가운데인 ④에서 시작해 양쪽으로 좁힌다.

  1. ④ 근거 청크가 top-k 안에 있는가(hit)? 골든셋의 근거 문장을 온전히 담은 청크가 검색 결과에 있는지 본다.
  2. 없으면 몇 위인가? k 바로 밖이면 k나 검색 방식(8주차)의 문제다. 어느 청크에도 근거가 온전히 없으면 ② 청킹이 잘랐거나(4주차) ① 문서가 깨진 것이다(3주차).
  3. 있으면 ⑤ 프롬프트를 읽는다. 근거가 들어갔나? 사람이 읽어도 답이 나오는 글인가?
  4. 그래도 틀리면 그때 ⑥ 생성을 본다. 시스템 지시, 모델, 온도(temperature)를 바꿔 본다.
증상먼저 볼 곳이번 주 예

최소 구현 코드

core 모듈을 쓰면 파이프라인 전체가 20줄 남짓이다. 아래 코드는 임베딩 모델과 API 키가 필요해 ▶ 실행 상자로 두지 않았다. 실습 위젯이 바로 이 흐름을 돌린다.

import { chunk } from '/assets/js/core/chunker.js';
import { loadModel, embed, embedBatch } from '/assets/js/core/embed.js';
import { VectorStore } from '/assets/js/core/vectorstore.js';
import { generate, ragPrompt } from '/assets/js/core/llm.js';

// ── 색인 단계: 문서가 바뀔 때 한 번 ──
const { documents } = await (await fetch('/assets/data/corpus/corpus.json')).json();
const chunks = documents.flatMap((d) =>
  chunk(d.text, { strategy: 'recursive', size: 200 })
    .map((c) => ({ ...c, id: `${d.id}#${c.index}`, doc: d.id })));
await loadModel('Xenova/multilingual-e5-small');
const vectors = await embedBatch(chunks.map((c) => c.text), { role: 'passage' });
const store = new VectorStore();
chunks.forEach((c, i) => store.add(c.id, vectors[i], c));

// ── 질의 단계: 질문마다 ──
async function answer(question, k = 3) {
  const q = await embed(question, { role: 'query' });
  const hits = store.search(q, k);                          // ④
  const prompt = ragPrompt(question, hits.map((h) => h.meta)); // ⑤
  const { text } = await generate({ provider: 'anthropic', ...prompt }); // ⑥
  return { text, sources: hits.map((h) => h.id) };
}

반환값에 sources를 함께 돌려주는 것이 중요하다. 답만 돌려주면 나중에 “왜 이 답이 나왔나”를 추적할 수 없다. 11주차에는 이 id로 원문 위치를 찾아 인용을 하이라이트한다.

4실습

아래 위젯은 문서셋 전체로 위 코드를 실제로 돌린다. 모델을 내려받는 동안에도 ①·② 단계 결과가 먼저 보이고, 모델이 준비되면 ③~⑥이 자동으로 이어진다. 단계마다 걸린 시간과 산출물이 오른쪽 실행 결과 창(휴대폰에서는 위젯 아래)에 표시된다. 맨 위의 12칸은 골든셋 12문항 각각의 근거 청크가 몇 위로 검색됐는지 보여 준다.

API 키가 없어도 된다

①~⑤는 키 없이 전부 실제로 실행된다. ⑥은 키가 없으면 “예시 응답 · 수업용 작성 예시” 표시와 함께 수업용으로 작성한 예시 응답을 보여 준다(근거 검색 성공·실패 두 경우). 키를 넣으면 ⑤의 프롬프트 그대로 실제 LLM을 호출한다. 키는 이 탭의 sessionStorage에만 저장되고 탭을 닫으면 사라진다.

C2. answer(question) 파이프라인 함수★★

색인 단계(청킹 → BM25 색인)는 한 번만, 질의 단계(검색 → 프롬프트 → 생성)는 질문마다 실행되도록 answer(question, k)를 완성한다. 반환값에는 답과 함께 근거 청크 id(sources)를 넣는다. 세 질문 중 어느 답이 틀렸는지, 그 이유가 무엇인지 적는다.

// 가짜 LLM: 근거 문장 중 질문과 겹치는 토큰이 가장 많은 문장을 그대로 옮긴다
function mockGenerate({ messages }) {
  const [ctx, q] = messages[0].content.replace('근거 문서:\n', '').split('\n\n질문: ');
  const qt = new Set(tokenize(q));
  let best = { score: 0, text: '' };
  for (const src of ctx.split(/\n\n(?=\[\d+\] )/)) {
    const [, n, body = ''] = src.match(/^\[(\d+)\] ([\s\S]*)$/) ?? [];
    for (const sent of body.split(/(?<=[.!?])\s+|\n+/)) {
      const score = [...new Set(tokenize(sent))].filter((t) => qt.has(t)).length;
      if (score > best.score) best = { score, text: `${sent.trim()} [${n}]` };
    }
  }
  return { text: best.score >= 3 ? best.text : '문서에서 찾을 수 없다.' };
}

C3. 중간 산출물 로그 남기기★★

각 단계를 step(이름, 함수, 요약함수)로 감싸서 걸린 시간과 산출물 요약을 log에 쌓는다. 끝에 console.table(log)로 한눈에 본다. q10(RAG 수업 요일)을 넣었을 때 로그의 어느 줄에서 이미 실패가 보이는지 찾는다.

    for (const sent of body.split(/(?<=[.!?])\s+|\n+/)) {
      const score = [...new Set(tokenize(sent))].filter((t) => qt.has(t)).length;
      if (score > best.score) best = { score, text: `${sent.trim()} [${n}]` };
    }
  }
  return { text: best.score >= 3 ? best.text : '문서에서 찾을 수 없다.' };
}

6정리 & 다음 주 예고

  • RAG는 색인 단계(문서 → 청킹 → 임베딩 → 벡터스토어, 한 번)와 질의 단계(질문 임베딩 → 검색 → 프롬프트 → 생성, 매번)로 나뉜다. 두 단계는 같은 임베딩 모델로 연결된다.
  • 각 단계의 산출물 모양을 알고, 파이프라인 함수는 답과 함께 근거 id를 돌려준다.
  • LLM은 프롬프트에 든 것만 본다. 답이 틀리면 검색부터 확인한다: hit인가 → 몇 위인가 → 프롬프트 속 근거가 읽을 만한가 → 그다음이 생성이다.
  • 검색이 성공해도 깨진 문서(q11의 “5O%”)는 틀린 답을 만든다. 파싱 품질은 마지막 단계까지 따라온다.
