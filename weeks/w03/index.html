문서는 텍스트가 아니다

PDF, 스캔본, 웹페이지, 표는 저마다 다른 방식으로 텍스트가 되고, 그 과정에서 조용히 망가진다. 이번 주는 망가진 텍스트를 고치되, 고치다가 멀쩡한 텍스트를 망가뜨리지 않는 법을 익힌다.

1학습 목표

이번 주가 끝나면
  • 텍스트층 PDF, 스캔 PDF, HTML, 표가 각각 어떻게 텍스트가 되고 어떤 식으로 깨지는지 설명할 수 있다.
  • 머리글 제거·OCR 숫자 교정·중복 제거·표 행 복원 같은 정제 단계를 문서에 맞게 고르고, 과도한 정제가 멀쩡한 텍스트를 망가뜨리는 경우를 판별할 수 있다.
  • 정제한 텍스트 조각에 출처·페이지 메타데이터를 붙이는 코드를 작성할 수 있다.

2왜 필요한가

문서셋에는 스캔한 장학금 안내문이 들어 있다. 사람 눈에는 “지급액은 수업료의 50%이다”로 보이지만, 광학 문자 인식(OCR, Optical Character Recognition)이 뽑아낸 텍스트는 다음과 같다.

한국폴리텍대학 분당융합기술교육원     - 1 -
2025학년도 장 학 금 안 내
성적 우수 장학금은 직전 학기 평균 평 점이 4.0 이상인 학생에게 지급한 다. 지급액은 수업료의 5O% 이다.

“50%”의 0이 영문 대문자 O로 바뀌었다. 이제 “성적 우수 장학금 지급액은?”이라는 질문(골든셋 q11)에 무슨 일이 생기는지 따라가 본다.

망가진 한 글자가 파이프라인 끝까지 간다
  • 검색 — 키워드 검색은 “50%”를 토큰 50으로, 문서의 “5O%”를 5o로 쪼갠다. 둘은 일치하지 않는다.
  • 생성 — 운 좋게 이 청크가 검색되어도 LLM은 “5O%”를 그대로 인용하거나 “정확한 비율을 알 수 없다”고 답한다.
  • 평가 — 골든셋의 근거 인용문조차 「지급액은 수업료의 5O% 이다.」로 기록되어 있다. 파싱이 틀리면 정답지까지 틀린다.

시간표도 마찬가지다. HTML 표를 단순 추출하면 “월 1-3 딥러닝 305 김 교수 월 4-6 자연어 처리 306 이 교수 화 1-3 검색증강생성(RAG) …”처럼 모든 셀이 한 줄로 이어진다. “RAG 수업은 무슨 요일 몇 교시인가?”(q10)에 답하려면 어디서 한 행이 끝나는지 알아야 하는데, 그 정보가 사라졌다.

이후의 청킹·임베딩·검색·생성은 모두 파싱이 넘겨준 텍스트만 본다. 파싱에서 사라진 정보는 어떤 단계도 되살리지 못한다.

3개념

로더: 원본마다 텍스트를 얻는 방법이 다르다

원본텍스트를 얻는 방법흔한 깨짐도구 예
텍스트층 PDF파일에 저장된 글자와 좌표를 그대로 읽는다2단 편집의 읽기 순서 뒤섞임, 머리글·쪽 번호 반복, 줄 끝 하이픈pdf.js(브라우저), PyMuPDF, pdfplumber
스캔 PDF·이미지글자가 없고 그림만 있다. OCR이 픽셀을 보고 글자를 추정한다0↔O, 1↔l 치환, 음절 사이 공백, 오탈자Tesseract, 클라우드 OCR API
HTMLDOM을 파싱해 텍스트 노드를 모은다메뉴·푸터·광고 혼입, 같은 블록 반복DOMParser(브라우저), BeautifulSoup
표행·열 구조를 읽어야 한다. 텍스트만 이으면 구조가 사라진다셀이 한 줄로 이어져 행·열 관계 소실pdfplumber·Camelot(PDF 표), HTML은 <td>를 직접 읽음

여러 형식을 한 번에 받아 제목·본문·표 같은 요소로 나누고 메타데이터까지 붙여 주는 Unstructured 같은 라이브러리도 있다. 도구가 달라도 질문은 같다. 이 로더는 무엇을 잃어버리는가?

이 사이트는 PDF 라이브러리를 쓰지 않는다

설치 없이 브라우저에서 돌아가야 하므로, 문서셋에는 “단순한 로더가 뽑아낸 결과”(OCR 텍스트, 한 줄로 이어진 표, 크롤링한 웹페이지)가 이미 들어 있다. 이번 주는 그 결과를 고치는 정제에 집중한다. 직접 가진 .html 파일은 브라우저의 DOMParser로 텍스트로 바꿔 볼 수 있다.

메타데이터: 조각이 어디서 왔는가

로더는 텍스트와 함께 메타데이터를 넘겨야 한다. 최소한 출처(source)와 페이지(page)다.

{
  "text": "지급액은 수업료의 50% 이다.",
  "metadata": { "source": "broken-scan", "title": "2025학년도 장학금 안내 (스캔본)", "page": 1, "loader": "ocr" }
}
  • 인용 — 답변 옆에 “장학금 안내 1쪽”을 붙인다(11주차).
  • 필터 — “2025학년도 문서에서만 찾기” 같은 조건 검색을 한다.
  • 디버깅 — 틀린 답이 어느 문서 어느 쪽에서 왔는지 추적한다. loader: "ocr"이면 OCR 오류부터 의심한다.
  • 갱신 — 문서 하나가 바뀌면 그 source의 조각만 다시 임베딩한다.

페이지 번호는 정제하면서 지우는 대상이기도 하다. 그래서 지우기 전에 메타데이터로 옮겨 둔다(Challenge C5).

정제 단계와 부작용

정제는 규칙의 모음이다. 모든 규칙은 고치는 것과 망가뜨릴 수 있는 것이 함께 있다.

단계규칙잘못 쓰면
페이지 번호 제거줄 끝의 “- 2 -”, 숫자만 있는 줄본문의 번호 목록까지 지운다
중복 문단 제거공백을 정규화한 뒤 완전히 같은 문단은 하나만(드묾) 일부러 반복한 문단
머리글·바닥글 제거여러 번 반복되는 줄(숫자 무시), 메뉴·저작권 키워드중복 제거보다 먼저 돌리면 반복된 본문도 머리글로 알고 지운다
표 행 복원알려진 열 패턴(요일 + 교시)에서 행을 자른다패턴에서 벗어난 행은 추측이 된다
OCR 숫자 교정숫자에 붙은 O→0, l→1만문맥 없이 쓰면 MLOps → ML0ps
끊긴 단어 공백 병합한 글자 음절을 다음 단어에 붙인다표·웹 문서에 쓰면 “조 교수” → “조교수”

두 가지 원칙이 나온다. 첫째, 규칙은 문서 종류별로 켠다(스캔본용 규칙을 웹 문서에 쓰지 않는다). 둘째, 정제 결과는 눈이 아니라 사실로 검증한다. 정답을 아는 사실(골든셋)이 정제 후에도 올바른 형태로 남아 있는지 확인한다.

파싱 품질은 상한이다

파이프라인의 각 단계는 앞 단계가 넘겨준 것만 쓸 수 있다. 그래서 전체 정답률은 대략 각 단계 성공률의 곱을 넘지 못한다.

정답률 ≤ 파싱 보존율 × 청킹 보존율 × 검색 재현율 × 생성 정확도

골든셋 12문항 중 q10(표)과 q11(OCR) 두 문항의 근거가 파싱에서 깨지면 파싱 보존율은 10/12이다. 뒤 단계가 모두 완벽해도 정답률은 83%를 넘지 못한다. 이후 9주 동안 청킹·임베딩·리랭킹을 아무리 다듬어도 이 천장은 움직이지 않는다.

4실습

아래 위젯은 문서셋의 망가진 문서(⚠ 표시)를 불러와 정제 단계를 켜고 끄며 비교한다. 결과 창 왼쪽은 로더가 넘겨준 원문(지워진 부분은 빨간 취소선), 오른쪽은 정제본(새로 생기거나 바뀐 부분은 초록)이다. 위쪽의 사실 확인은 골든셋 사실과 추가 확인 항목이 정제본에 올바른 형태로 남아 있는지 보여 준다. 처음 화면은 모든 단계를 끈 상태, 즉 실패하는 상태다. 결과는 오른쪽 실행 결과 창에 실시간으로 표시된다.

관찰 질문

  1. 처음 화면(장학금 안내 스캔본, 모두 끄기)에서 ✗인 사실은 몇 개인가? “5O%”가 검색과 생성에서 각각 어떤 문제를 일으키는지 말로 설명한다.
  2. OCR 숫자 교정만 켠다. 몇 건이 바뀌었고, 어느 사실이 ✓가 되었나? 이어서 과도: 모든 O→0을 켜고 문서를 2학기 시간표로 바꾼다. 어떤 행이 망가지는가?
  3. 시간표에서 표 행 복원을 켠다. 「수 | 1-6 | 현장 실습 | 외부 산업체 | —」 행의 담당이 “—”인 이유는 무엇인가? 이 행은 원본에서 정말 그랬는지, 규칙이 추측한 것인지 구별할 수 있나?
  4. 끊긴 단어 공백 병합은 스캔본에서 무엇을 고치나? 같은 단계를 시간표와 자주 묻는 질문 문서에 켜면 무엇이 망가지나?
  5. 자주 묻는 질문 문서에서 머리글·바닥글 제거만 켠다. 노트북 Q&A는 어떻게 되나? 그다음 중복 문단 제거를 함께 켠다. 단계의 순서가 왜 중요한가?
  6. (선택) “직접 붙여넣기 · 파일 불러오기”에서 자신이 가진 .html 파일을 불러온다. 표는 어떻게 보이는가? 텍스트 규칙으로 표를 복원하는 것과 로더가 <td>를 읽는 것 중 어느 쪽이 믿을 만한가?

C2. 단어를 망가뜨리지 않는 OCR 숫자 교정★★

순진한 교정 replace(/O/g, '0')은 “MLOps”를 “ML0ps”로 만든다. 숫자와 붙어 있는 O·o·I·l만 고치고, 영어 단어의 일부인 글자는 건드리지 않는 fixOcr을 정규식으로 작성한다. 9개 사례를 모두 통과해야 한다. 힌트: 전방·후방 탐색 (?<![A-Za-z]), (?![A-Za-z]).

C4. 시간표 행을 객체로 복원★★★

C5. 정제된 청크에 출처·페이지 붙이기★★★★

스캔본의 쪽 번호 줄(“… - 2 -”)은 지워야 할 잡음이지만, 동시에 이 텍스트가 몇 쪽인지 알려 주는 유일한 정보다. 쪽 번호 줄을 경계로 페이지를 나누고, 페이지마다 OCR을 교정해 청킹한 뒤 각 청크에 { source, title, page, start, end } 메타데이터를 붙인다. 마지막으로 “50%”와 “10시간”이 몇 쪽에서 나왔는지 출력한다.

const corpus = await (await fetch('/assets/data/corpus/corpus.json')).json();

const fixOcr = (t) =>
  t.replace(/(?<![A-Za-z])[0-9OoIl]*\d[0-9OoIl]*(?![A-Za-z])/g, (r) => r.replace(/[Oo]/g, '0').replace(/[Il]/g, '1'));

function splitPages(text) {

  // TODO: 줄 단위로 돌면서 /-\s*(\d+)\s*-\s*$/에 맞는 줄을 만나면 새 페이지를 시작한다

  return pages;

const chunks = splitPages(doc.text).flatMap(({ page, text }) =>

for (const q of ['50%', '10시간']) {

6정리 & 다음 주 예고

  • 로더는 원본 종류마다 다르고, 깨지는 모양도 다르다. 텍스트층 PDF는 머리글·읽기 순서, 스캔본은 OCR 오류, HTML은 메뉴·중복, 표는 구조 소실이 대표적이다.
  • 정제 규칙은 고치는 것과 망가뜨리는 것이 함께 있다. 문서 종류별로 켜고, 순서(중복 제거 → 머리글 제거)를 지킨다.
  • 정제 결과는 골든 사실로 검증한다. 파싱을 고치면 골든셋의 근거 인용문도 함께 고친다.
  • 페이지·출처는 지우기 전에 메타데이터로 옮긴다. 인용·필터·디버깅이 모두 여기서 시작한다.
  • 파싱 보존율은 이후 모든 단계의 상한이다.

다음 주(4주차 청킹 전략)에는 이번 주에 정제한 텍스트를 검색 단위로 자른다. 고정 길이·문장 단위·재귀 분할로 잘라 보고, 근거 문장이 청크 경계에서 잘리는 조건과 오버랩의 비용을 측정한다. 표가 깨진 시간표를 청킹 위젯에 넣으면 어떻게 되는지도 다시 확인한다.
