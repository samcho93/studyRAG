→ 누가 더 나은지, 왜인지 아무도 모른다

고정하는 세 가지

  1. 같은 골든셋 (12문항)
  2. 같은 결과 형식 (JSON)
  3. 같은 k

발문: “B팀의 90%와 A팀의 시연 중 무엇을 믿겠나?” → 둘 다 믿을 수 없다는 답을 끌어낸다. 조건이 다르면 숫자도 비교할 수 없다.

9주차 평가와 이어진다. 오늘은 그 평가를 팀 사이로 넓힌 것이다.

결과 JSON 스키마

{
  "team": "3조 · 하이브리드",
  "members": ["김OO", "이OO", "박OO"],
  "system": { "chunking": "recursive 200 / overlap 20",
              "embedding": "Xenova/multilingual-e5-small",
              "retriever": "hybrid (RRF k=60)", "k": 5,
              "reranker": null, "llm": "gpt-4.1-mini" },
  "golden": [ { "id": "q01",
      "retrieved": ["facility-rules#1", "dept-overview#2"],
      "answer": "최대 12시간이다.", "citations": ["facility-rules#1"] } ],
  "notes": "q10은 표 파싱 실패"
}

학생이 자주 틀리는 곳: "k": "5"(따옴표), members를 쉼표 문자열로 적기, citations를 빈 문자열로 두기. 모두 “스키마 오류 파일” 예시에 들어 있다.

시스템 내부는 자유, 밖으로 내는 형식만 고정한다는 점을 강조한다.

채점 방식

  • 청크 ID → 문서 ID: rag-hybrid#2 → rag-hybrid
  • 같은 문서의 두 번째 청크부터는 자리만 차지, 점수는 한 번
  • 문항당 근거 문서 1개 → Recall@k = Hit@k
  • nDCG: 1위 1.0 · 2위 0.63 · 3위 0.5
  • 근거 인용률: 근거 문서를 인용한 답변 비율

Faithfulness는 자동 채점하지 않는다 → 실패 사례 발표에서 사람이 본다

발문: “같은 문서 청크 세 개를 1~3위에 올리면 Recall은?” 중복을 제거하지 않으면 3/1 = 3이 된다. core/metrics.js의 recallAtK는 중복을 가정하지 않으므로 채점 전에 정규화해야 한다.

MRR도 k 밖은 0으로 자른다(MRR@k). 팀마다 k가 다르면 긴 목록이 유리해지기 때문이다.

발표 순서는 전날 추첨으로 정해 공지한다. 점수판을 먼저 공개하면 발표가 “숫자 자랑”이 아니라 “숫자 해석”이 된다.

각 팀이 발표하는 동안 청중 팀은 질문 카드 한 장씩을 쓴다(질문 가이드 슬라이드 참고). 좋은 질문을 한 팀에 수업 참여 점수를 준다.

데모 · 팀별 결과 업로드 · 점수판

시연 순서 (점수판은 오른쪽 실행 결과 창에 나온다)

  1. 처음 화면: 예시 팀 3개, k=5. A 0.813 / C 0.683 / B 0.298 (nDCG)
  2. MRR@k 열을 눌러 정렬 → 순서는 같지만 A·C 격차가 Recall보다 작다(0.778 vs 0.632)
  3. k=1 → 전원 실패 문항이 q10 하나에서 q10·q11·q12 세 개로 는다
  4. “스키마 오류 파일” → ✗ 오류 8개. 각 메시지를 읽어 준다
  5. “JSON 문법 오류” → 행·열 위치가 나온다
  6. 실제 팀 JSON을 끌어 놓아 점수판에 올린다. ⛶ 크게 보기로 투영한다

오프닝 15분 안에서 1, 2, 4번만 짧게 다룬다. 3·5번은 학생용 페이지 과제로 넘긴다.

4번 정답: 검색된 문서 자체가 OCR 오류(5O%)를 담고 있어 LLM이 그대로 옮겼다. Recall은 성공으로 세므로 지표로는 안 보인다 → 사람이 답을 읽어야 하는 이유.

코드로 확인하기

import { evaluate } from '/assets/js/core/metrics.js';
const golden = await (await fetch('/assets/data/golden/golden.json')).json();
const K = 5;
const rows = [];
for (const f of ['sample-team-a', 'sample-team-b', 'sample-team-c']) {
  const t = await (await fetch(`/assets/data/w12/${f}.json`)).json();
  const runs = golden.items.map((item) => {
    const seen = new Set();
    const ids = (t.golden.find((q) => q.id === item.id)?.retrieved ?? [])
      .map((id) => id.split('#')[0])
      .map((d) => (seen.has(d) ? null : (seen.add(d), d)));
    return { retrieved: ids.slice(0, K), relevant: item.evidence.map((e) => e.doc) };
  });
  const m = evaluate(runs, K);
  rows.push({ team: t.team, recall: m.recall, mrr: m.mrr, ndcg: m.ndcg });
}
console.table(rows);

기대 출력(k=5): A 0.9167 / 0.7778 / 0.8135, B 0.5 / 0.2319 / 0.2983, C 0.8333 / 0.6319 / 0.6827.

부록 B · C1 정답

const good = await (await fetch('/assets/data/w12/sample-team-a.json')).json();
const bad = await (await fetch('/assets/data/w12/sample-broken.json')).json();
const isStr = (v) => typeof v === 'string' && v.trim() !== '';

function validate(r) {
  const errors = [];
  if (!isStr(r.team)) errors.push('team: 비어 있지 않은 문자열이어야 한다');
  if (!Array.isArray(r.members) || !r.members.every(isStr)) errors.push('members: 문자열 배열이어야 한다');
  const k = r.system?.k;
  if (!Number.isInteger(k) || k < 1) errors.push(`system.k: 1 이상의 정수여야 한다 (지금 ${JSON.stringify(k)})`);
  if (!Array.isArray(r.golden)) errors.push('golden: 배열이어야 한다');
  else r.golden.forEach((q, i) => {
    if (!Array.isArray(q.retrieved)) errors.push(`golden[${i}].retrieved: 배열이어야 한다`);
    if (typeof q.answer !== 'string') errors.push(`golden[${i}].answer: 문자열이어야 한다`);
    if (!Array.isArray(q.citations)) errors.push(`golden[${i}].citations: 배열이어야 한다`);
  });
  return errors;
}
console.log('A:', validate(good));
console.log('broken:', validate(bad));

기대: A → [], broken → 6개 (team, members, system.k, golden[0].retrieved, golden[1].retrieved, golden[3].citations).

위젯 검증기는 여기에 두 가지를 더 본다: 골든셋에 없는 id(q99), 중복 id(q01 두 번) → 오류 8개. 학생에게 “무엇을 더 검사해야 하나”를 묻는 확장 과제로 쓴다.

왜: typeof []는 'object'이므로 배열은 반드시 Array.isArray로 본다. "5"는 Number.isInteger에서 걸러진다.

부록 B · C2 정답

import { evaluate } from '/assets/js/core/metrics.js';
const golden = await (await fetch('/assets/data/golden/golden.json')).json();
const team = await (await fetch('/assets/data/w12/sample-team-c.json')).json();
const K = 5;

function toDocRanking(ids) {
  const seen = new Set();
  return ids.map((id) => {
    const d = id.split('#')[0];
    if (seen.has(d)) return null;
    seen.add(d);
    return d;
  });
}
let cite = 0, citeOk = 0;
const runs = golden.items.map((item) => {
  const sub = team.golden.find((q) => q.id === item.id);
  const relevant = item.evidence.map((e) => e.doc);
  const cited = (sub?.citations ?? []).map((c) => c.split('#')[0]);
  if (cited.length) cite++;
  if (cited.some((d) => relevant.includes(d))) citeOk++;
  return { retrieved: toDocRanking(sub?.retrieved ?? []).slice(0, K), relevant };
});
const n = golden.items.length;
console.log(evaluate(runs, K), { cite: cite / n, citeOk: citeOk / n });

기대(예시 팀 C, k=5): recall 0.8333, precision 0.1667, hit 0.8333, mrr 0.6319, ndcg 0.6827, cite 0.8333, citeOk 0.8333.

왜 null인가: 중복 청크를 지우면(filter) 뒤 문서의 순위가 당겨져 MRR·nDCG가 부풀려진다. 자리는 두고 점수만 막는다. 예시 팀 C의 q04는 rag-embedding#1, rag-chunking#2, rag-chunking#1… → 근거가 2위.

부록 B · C3 정답

import { evaluate } from '/assets/js/core/metrics.js';
const golden = await (await fetch('/assets/data/golden/golden.json')).json();
const files = ['sample-team-a', 'sample-team-b', 'sample-team-c'];
const teams = await Promise.all(files.map(async (f) => (await fetch(`/assets/data/w12/${f}.json`)).json()));
function score(team, k) {
  const runs = golden.items.map((item) => {
    const seen = new Set();
    const ids = (team.golden.find((q) => q.id === item.id)?.retrieved ?? [])
      .map((id) => id.split('#')[0]).map((d) => (seen.has(d) ? null : (seen.add(d), d)));
    return { retrieved: ids.slice(0, k), relevant: item.evidence.map((e) => e.doc) };
  });
  return evaluate(runs, k);
}
const K = 5;
const rows = teams.map((t) => ({ team: t.team, ...score(t, K) })).sort((a, b) => b.ndcg - a.ndcg);
const f = (v) => v.toFixed(3);
const lines = [`| 순위 | 팀 | Recall@${K} | MRR@${K} | nDCG@${K} |`, '|---|---|---:|---:|---:|',
  ...rows.map((r, i) => `| ${i + 1} | ${r.team} | ${f(r.recall)} | ${f(r.mrr)} | ${f(r.ndcg)} |`)];
console.log(lines.join('\n'));

기대 출력:

| 순위 | 팀 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---:|---:|---:|
| 1 | 예시 팀 A · 하이브리드+리랭킹 | 0.917 | 0.778 | 0.813 |
| 2 | 예시 팀 C · BM25 단독 | 0.833 | 0.632 | 0.683 |
| 3 | 예시 팀 B · 벡터 단독 | 0.500 | 0.232 | 0.298 |

---:는 오른쪽 정렬이다. 숫자 열은 오른쪽 정렬해야 자릿수 비교가 쉽다. 팀 이름에 |가 있으면 표가 깨진다 → \|로 바꾸는 것이 확장 과제.

}

  const failed = golden.items.filter((item) => teams.every((t) => rankOf(t, item, k) === null));
  console.log(`k=${k}: 전원 실패 ${failed.length}문항`);
  console.table(failed.map((it) => ({
    id: it.id, question: it.question,
    evidence: it.evidence.map((e) => e.doc).join(', '), note: it.note ?? '',
  })));
}

기대: k=1 → q10, q11, q12 (세 문항 모두 broken-* 문서) · k=3 → q10 · k=5 → q10.

여기서는 첫 적중 순위만 보므로 중복 청크 처리가 필요 없다(첫 등장 위치는 변하지 않는다). 토론: 전원 실패는 팀의 실수가 아니라 데이터 문제일 가능성이 크다. q10은 표가 한 줄로 뭉개진 문서라 어떤 검색기로도 “화요일 1-3교시”를 찾기 어렵다 → 3주차 파싱으로 돌아간다.

import { evaluate } from '/assets/js/core/metrics.js';

const K = 5;

function perQuestion(team) {
  return golden.items.map((item) => {
    const seen = new Set();
    const retrieved = (team.golden.find((q) => q.id === item.id)?.retrieved ?? [])
      .map((id) => id.split('#')[0]).map((d) => (seen.has(d) ? null : (seen.add(d), d))).slice(0, K);
    const relevant = item.evidence.map((e) => e.doc);
    const i = retrieved.findIndex((d) => d !== null && relevant.includes(d));
    return { id: item.id, retrieved, relevant, rank: i === -1 ? null : i + 1 };
  });
}
const a = perQuestion(base), b = perQuestion(cand);
const ma = evaluate(a, K), mb = evaluate(b, K);
console.table(['recall', 'mrr', 'ndcg'].map((m) => ({ metric: m, base: ma[m], cand: mb[m], delta: mb[m] - ma[m] })));

const r = (x) => x.rank ?? K + 1;
const better = [], worse = [], same = [];
a.forEach((qa, i) => {
  const qb = b[i], label = `${qa.id} ${qa.rank ?? '✗'}→${qb.rank ?? '✗'}`;
  (r(qb) < r(qa) ? better : r(qb) > r(qa) ? worse : same).push(label);
});

  • 인용: 인용 청크에 답 문장이 실제로 있음

감점 · 0점 처리

  • retrieved를 손으로 수정 → 평가 항목 0점
  • API 키 노출 → 즉시 폐기 안내, −5
  • 마감 후 제출 → 하루 −2
  • 발표 12분 초과 → −1

retrieved 수정 여부는 질의응답에서 “이 질문을 지금 서비스에 넣어 보자”로 확인한다. 라이브 결과가 JSON과 크게 다르면 재현성을 묻는다.

API 키가 저장소에 있으면 발표 전에 발견해 키 폐기부터 안내한다. 공개 저장소 키는 몇 분 안에 수집된다.
