1학습 목표

이번 주가 끝나면
  • 팀 시스템의 결과를 정해진 JSON 스키마로 내보내고 스스로 검증할 수 있다.
  • 여러 팀의 시스템을 같은 골든셋에서 Recall@k·MRR·nDCG·인용률로 비교하고 차이를 해석할 수 있다.
  • 문제·설계·평가 결과·실패 사례·개선 순서로 근거 있는 발표를 구성할 수 있다.

2왜 필요한가

공통 형식과 공통 채점 없이 발표하면 어떻게 될까. A팀은 잘 되는 질문 세 개를 골라 시연한다. B팀은 “검색 정확도 90%”라고 말하지만 k=20에서, 직접 만든 쉬운 질문으로 잰 값이다. C팀은 답변이 그럴듯하니 잘 된다고 말한다. 세 발표를 다 들어도 어느 시스템이 더 나은지, 왜 그런지 아무도 모른다.

데모 세 개로는 아무것도 증명되지 않는다

시연 질문은 발표자가 고른다. 성공한 질문만 보여 주면 실패는 드러나지 않는다. 9주차에 본 것처럼, 골든셋 12문항 중 표가 깨진 문서(q10)와 OCR 오류 문서(q11)에서 대부분의 시스템이 실패한다. 이 실패를 숨긴 발표와 원인까지 설명한 발표는 같은 점수를 받을 수 없다.

그래서 이번 발표는 세 가지를 고정한다. 같은 골든셋(golden.json 12문항), 같은 결과 형식(아래 JSON 스키마), 같은 k. 이 세 가지가 같아야 숫자가 비교 가능해지고, 숫자가 비교 가능해야 “설계를 바꿔서 좋아졌다”는 말을 믿을 수 있다.

결과 JSON 스키마

팀 시스템이 골든셋 질문 12개를 실제로 처리한 결과를 그대로 기록한다. 검색 결과(retrieved)는 순위 순서대로, 문서 ID나 문서ID#청크번호 형식의 청크 ID로 적는다.

필드형식설명
team문자열 · 필수팀 이름. 같은 이름으로 다시 올리면 교체된다
members문자열 배열 · 필수팀원 이름 (3~4명 권장)
system객체 · 필수chunking, embedding, retriever(문자열), k(정수), reranker, llm(문자열 또는 null)
golden[]배열 · 필수문항마다 { id, question?, retrieved[], answer, citations[] }. id는 q01~q12
notes문자열 · 선택설계 의도, 알려진 한계 등 자유 메모

  "members": ["김OO", "이OO", "박OO"],

  "notes": "q10은 표 파싱 실패로 검색되지 않는다."
}

채점 방식

골든셋의 근거(evidence)는 문서 단위로 주어진다. 그래서 청크 ID는 # 앞의 문서 ID로 바꿔 채점한다. 같은 문서의 청크가 여러 번 나오면 첫 번째만 점수에 들어가고, 나머지는 순위 자리만 차지한다. 그렇지 않으면 같은 문서 청크 3개로 Recall이 1을 넘는 일이 생긴다.

지표뜻 (이번 골든셋은 문항당 근거 문서 1개)
Recall@k상위 k개 안에 근거 문서가 있으면 1, 없으면 0 → 12문항 평균
MRR@k근거 문서 순위 r의 역수 1/r (k 밖이면 0) → 평균. 1위가 많을수록 높다
nDCG@k근거가 r위면 1/log₂(r+1). 1위 1.0, 2위 0.63, 3위 0.5
인용률인용을 하나 이상 단 답변의 비율
근거 인용률골든셋 근거 문서를 인용한 답변의 비율. 인용했지만 엉뚱한 문서라면 세지 않는다

k는 점수판에서 모든 팀에 똑같이 적용한다. 팀이 k=10으로 제출해도 k=5로 채점하면 상위 5개만 본다. 생성 품질(Faithfulness)은 자동 채점하지 않고, 발표에서 실패 사례와 함께 사람이 판단한다.

발표 구성 (10분)

  1. 문제 (1분) — 누가 무엇을 묻는 서비스인가. 대표 질문 하나.
  2. 설계 (2분) — 청킹·임베딩·검색·리랭킹·LLM 선택과 그 이유. 결과 JSON의 system과 일치해야 한다.
  3. 평가 결과 (3분) — 점수판의 우리 팀 숫자. 같은 k에서 Recall@k·MRR·nDCG·근거 인용률.
  4. 실패 사례 (2분) — 틀린 문항 두 개 이상. 파싱·청킹·검색·생성 중 어느 단계에서 실패했는지 증거로 보인다.
  5. 개선 (2분) — 바꾼 설정 하나와 전후 점수 차이. 좋아진 문항과 나빠진 문항을 모두 말한다.

평가 루브릭과의 연결

팀 프로젝트는 성적의 40%다(교과목 안내, 골든셋 q02). 또한 팀 프로젝트 최종 발표 통과는 학과 수료 요건이다(q03). 40점은 다음과 같이 나눈다.

항목배점무엇을 보나
동작하는 서비스10질문 → 답변 + 인용이 실제로 동작한다. 근거가 없으면 모른다고 답한다
평가와 재현성10결과 JSON이 검증을 통과하고, 발표 숫자와 점수판 숫자가 같다
실패 분석8실패 원인을 파이프라인 단계로 특정하고 증거를 보인다
개선 실험7같은 골든셋·같은 k에서 설정 하나를 바꾼 전후 비교
발표·질의응답510분 안에 5개 구성을 전달하고 질문에 근거로 답한다

점수판 순위 자체는 배점이 아니다. 점수가 낮아도 실패를 정확히 분석하고 개선을 증명한 팀이 더 높은 점수를 받을 수 있다.

4실습

아래 점수판에는 예시 팀 세 개의 결과 파일(assets/data/w12/sample-team-*.json)이 미리 올라가 있다. 가상의 팀이며, 각자 다른 설계를 골랐다. 팀 결과 JSON을 끌어 놓거나 파일 선택으로 올리면 즉시 검증·채점되어 점수판에 추가된다. 파일은 브라우저 안에서만 읽고 어디에도 보내지 않는다. 점수판과 문항별 적중 지도는 오른쪽 실행 결과 창에 표시된다.

  3. 예시 팀 B는 어떤 임베딩 모델을 썼나? 5주차에 본 실패와 같은 현상인지 문항별 적중 지도에서 확인한다.
  4. 예시 팀 C의 q11 칸에 마우스를 올려 답변을 읽는다. 검색은 성공했는데 답이 틀린 이유는 무엇인가? 이 실패는 Recall로 드러나는가?
  5. 스키마 오류 파일과 JSON 문법 오류 버튼을 누른다. 각 오류 메시지를 보고 파일을 어떻게 고쳐야 하는지 말할 수 있는가? 오류 파일은 왜 점수판에 오르지 않는가?
  6. 샘플 JSON 내려받기로 받은 템플릿을 그대로 올리면 통과하는가? 통과해도 점수가 0인 이유는?

import { evaluate } from '/assets/js/core/metrics.js';

const golden = await (await fetch('/assets/data/golden/golden.json')).json();
const files = ['sample-team-a', 'sample-team-b', 'sample-team-c'];
const teams = await Promise.all(files.map(async (f) => (await fetch(`/assets/data/w12/${f}.json`)).json()));

function score(team, k) {
  const runs = golden.items.map((item) => {
    const seen = new Set();
    const ids = (team.golden.find((q) => q.id === item.id)?.retrieved ?? []).map((id) => {
      const d = id.split('#')[0];
      if (seen.has(d)) return null;
      seen.add(d);
      return d;
    });
    return { retrieved: ids.slice(0, k), relevant: item.evidence.map((e) => e.doc) };
  });
  return evaluate(runs, k); // { recall, precision, hit, mrr, ndcg }
}

6정리 & 12주 돌아보기

  • 비교하려면 세 가지를 고정한다: 같은 골든셋, 같은 결과 형식, 같은 k.

  • 점수는 순위가 아니라 대화의 출발점이다. 모든 팀이 놓친 문항은 대개 데이터(파싱) 문제다.
