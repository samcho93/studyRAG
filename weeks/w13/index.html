“주말에는?”을 검색하면 무엇이 나올까

사람은 대화를 이어서 묻는다. 그런데 지금까지 만든 RAG는 질문 하나만 보고 검색한다. 이번 실습은 4~11주차에 만든 검색·생성·인용을 대화로 확장해, 후속 질문을 대화 기록으로 다시 써서 검색하는 학과 안내 챗봇을 만든다.

1학습 목표

이번 실습이 끝나면
  • 단일 질문 RAG와 대화형 RAG의 차이를 설명하고, 후속 질문이 검색에 실패하는 원인을 대명사·생략으로 짚을 수 있다.
  • 대화 기록으로 후속 질문을 독립 질문으로 재작성하는 규칙과 condense 프롬프트를 작성하고, 원문과 재작성 질문의 hit@3를 비교할 수 있다.
  • 대화 기록 창 크기, 되묻기 기준, 개인정보 가리기 같은 대화형 서비스의 운영 규칙을 정할 수 있다.

2왜 필요한가

11주차까지 만든 RAG에 학과 안내 문서를 넣고 학생이 챗봇처럼 이어서 묻는다고 하자. 첫 질문 “실습실은 몇 시까지 열어?”는 잘 된다. 문제는 두 번째 질문부터다.

질문 하나만 보고 검색한 챗봇

학생 실습실은 몇 시까지 열어?
챗봇 실습실은 수업 시간 외에도 평일 오후 9시까지 개방된다 [1].

학생 주말에는?
챗봇 주말에는 토요일만 오전 10시부터 오후 5시까지 열고, 일요일과 공휴일에는 휴관한다 [1]. ← 도서관 안내

학생 신청은 언제까지 해야 해?
챗봇 외박 신청은 금요일 오후 6시까지 사감실에 해야 한다 [1]. ← 기숙사 안내

두 답 모두 인용이 붙어 있고 출처 문서에 실제로 있는 문장이다. 11주차의 인용 검증기로도 잡히지 않는다. 틀린 곳은 생성이 아니라 검색에 들어간 질문이다. 검색기는 “주말에는?”이라는 네 글자만 받았으니, 주말 이야기가 가장 많은 도서관·행정실·통학 버스 문서를 돌려준 것이 오히려 정상이다. 실습실 문서는 상위 3개에도 들지 못했다.

사람에게 “주말에는?”은 “실습실은 주말에도 여나?”이다. 앞 대화가 생략된 주제를 채워 주기 때문이다. 대화형 RAG가 할 일은 이것을 기계적으로 해 주는 것이다. 검색하기 전에 후속 질문을 대화 기록으로 다시 써서 혼자서도 뜻이 통하는 질문으로 만든다.

대화 기록을 통째로 검색어에 붙이면 안 될까? 안 된다. “실습실은 몇 시까지 열어? 주말에는? 신청은 언제까지 해야 해?”를 한 번에 검색하면 세 주제가 섞여 BM25 점수와 임베딩이 모두 흐려진다(4주차의 “큰 청크” 문제와 같다). 검색에는 지금 묻는 것 하나만 담은 짧은 질문이 좋다.

질문 재작성(condense)

질문 재작성(query rewriting)은 후속 질문을 대화 기록 없이도 이해되는 독립 질문(standalone question)으로 바꾸는 단계다. 대화 기록을 “압축”해 질문에 녹인다는 뜻에서 condense라고도 부른다. 두 가지 방법이 있다.

방법하는 일장점약점
규칙 기반주제어 사전으로 앞 질문의 주제를 찾아 붙이고 대명사를 바꾼다키·비용이 없다, 결과를 설명할 수 있다사전에 없는 주제, 챗봇 답변 속 대상은 못 찾는다
LLM condense대화 기록과 질문을 프롬프트로 주고 독립 질문을 쓰게 한다답변 속 대상, 복잡한 생략도 푼다호출이 한 번 늘고, 가끔 질문에 답해 버리거나 내용을 지어낸다

위젯의 규칙 기반 재작성기는 세 규칙만 쓴다. ① 대명사(거기, 그거)는 최근 질문의 주제어로 바꾼다. ② 주제어가 없는 짧은 질문이나 “그럼·그리고”로 시작하는 질문에는 최근 질문의 주제어를 앞에 붙이고, 바로 앞 질문도 후속 질문이었다면 그 핵심어(“주말”)도 함께 붙인다. ③ “그럼 딥러닝은?”처럼 주제만 바뀐 질문에는 앞 질문의 나머지(“선수 과목은?”)를 붙인다. 주제어를 못 찾으면 추측하지 않고 되묻는다.

LLM condense 프롬프트는 아래와 같다. 답하지 말고 질문만 쓰라는 규칙과, 모르면 되묻기로 표시하라는 규칙이 핵심이다.

[system]
너는 학과 안내 챗봇의 질문 재작성기다. 대화 기록과 마지막 질문을 읽고,
기록 없이도 뜻이 통하는 검색용 독립 질문 한 문장으로 다시 쓴다.
규칙: 1) 대명사(거기, 그거)와 생략된 주제를 기록에 나온 구체적인 이름으로 바꾼다.
2) 마지막 질문이 이미 독립적이면 그대로 쓴다. 3) 답하지 말고 질문만 출력한다.
4) 기록으로도 무엇을 묻는지 알 수 없으면 '되묻기: '로 시작하는 확인 질문을 쓴다.
5) 학번·전화번호 같은 개인정보는 질문에 넣지 않는다.

챗봇 답변의 인용 번호 [1]은 지우고 넣는다. 재작성에는 필요 없고, 이전 턴의 [1]과 이번 턴의 [1]이 다른 출처라서 모델을 헷갈리게 한다. 답변은 앞부분만 잘라 넣어도 대상(“학과 행정실”)을 찾기에 충분하다.

네 번째 줄이 규칙의 한계다. 규칙은 사용자 질문만 보기 때문에 “거기”를 최근 질문의 주제어인 실습실로 바꾸고, 검색은 실습실 규정을 1위로 가져오지만 거기에는 층 정보가 없다. 위젯의 챗봇은 결국 되묻는데, 내미는 선택지(실습실 이용 규정, 자주 묻는 질문, 딥러닝 교과목 안내)에 정작 학과 행정실이 없다. 틀린 재작성은 검색과 되묻기까지 모두 엉뚱한 방향으로 이끈다. 재작성 결과를 로그로 남기고 점검해야 하는 이유다.

대화 기록 창 크기와 토큰

재작성에 기록을 얼마나 보여 줄지가 창 크기(window)다. 최근 N턴만 넣는다. 아래는 “실습실 이용” 시나리오의 3·4번째 질문을 창 크기별로 규칙 기반 재작성한 결과와, 4번째 질문의 condense 프롬프트 길이다.

창 크기“신청은 언제까지 해야 해?”“거기는 몇 층에 있어?”프롬프트 길이
0턴그대로 (기숙사 문서 1위)되묻기300자
1턴그대로 — 1턴 전 “주말에는?”에 주제어가 없다 (기숙사 1위)되묻기352자
2턴실습실 주말 신청은 언제까지 해야 해? ✓되묻기403자
3턴실습실 주말 신청은 언제까지 해야 해? ✓실습실 몇 층에 있어? ✗459자

창이 작으면 주제를 잃는다. 창이 크면 비용이 늘고, 오래된 주제가 끼어들 기회도 는다. 4번째 질문은 창이 작을 때 되묻고(안전), 창이 클 때 틀린 대상을 고른다(위험). 비용은 이렇게 늘어난다. 한 턴이 평균 c자이고 창이 N턴이면 재작성 프롬프트는 턴마다 약 s + N·c자다(s는 시스템 프롬프트). 창을 두지 않고 기록 전체를 넣으면 t번째 턴의 프롬프트가 s + t·c자로 계속 커지고, 대화 전체 비용은 턴 수의 제곱에 비례해 늘어난다. 이 실습에서는 토큰을 한국어 1자 ≈ 1토큰으로 어림한다(토크나이저마다 다르다, 1주차).

실무에서는 두 가지를 함께 쓴다. 턴 수로 자르고(최근 N턴), 글자·토큰 예산으로 한 번 더 자른다(Challenge C1). 예산을 넘으면 가장 오래된 턴부터 버리고, 중간 턴을 건너뛰어 순서를 깨지 않는다. 오래된 대화를 요약 한 줄로 남기는 방법도 있지만 요약도 LLM 호출이다.

답변의 인용은 턴마다 새로

대화형이어도 인용 규칙(11주차)은 그대로다. 매 턴 재작성 질문으로 다시 검색하고, 이번 턴에 검색한 출처에만 번호를 붙인다. 이전 턴의 출처를 재사용하면 “[1]”이 무엇을 가리키는지 사용자가 알 수 없게 된다. 위젯의 답변 밑에 출처 제목을 턴마다 다시 적는 이유다. 답변은 재작성 질문에 대해 만들되, 화면에는 사용자가 쓴 원래 질문을 보여 준다.

실패하면 되묻기

되묻기(clarifying question)는 추측 대신 사용자에게 확인하는 응답이다. 두 경우에 되묻는다.

  • 재작성 실패: 대명사나 “그럼”이 있는데 기록에서 주제어를 찾지 못했다 (“그거 언제까지 내야 해?”가 첫 질문).
  • 검색 실패: 재작성한 질문의 BM25 최고 점수가 기준 τ보다 낮다. 위젯은 τ = 3을 쓴다. “점심 메뉴 뭐야?”(2.45)처럼 문서에 없는 질문이 여기에 걸린다. Challenge C4에서 이 기준을 라벨 붙인 질문으로 다시 정한다.

되물을 때는 후보를 보여 준다. 검색 상위 문서의 제목(“학사 행정 안내”, “기숙사 생활 안내” …)을 선택지로 주면 사용자가 한 번에 고를 수 있다. BM25 점수는 질문 길이에 따라 커지므로 문서셋이 바뀌면 τ도 다시 정해야 한다.

개인정보를 기록에 남기지 않기

대화형 서비스에는 단일 질문 RAG에 없던 저장소가 생긴다. 바로 대화 기록이다. 학생이 “내 학번은 2025123456이야”라고 쓰면 그 문장은 기록에 남고, 다음 턴마다 재작성 프롬프트에 실려 외부 LLM으로 전송된다. 그래서 순서를 지킨다.

  1. 입력을 받자마자 전화번호·학번·이메일·주민등록번호를 정규식으로 [학번]처럼 가린다.
  2. 가린 문장만 기록에 저장하고 프롬프트에 넣는다. 원문은 어디에도 남기지 않는다(콘솔 로그 포함).
  3. 기록은 브라우저 메모리에만 두고 새로고침이나 “대화 초기화”로 지운다. 이 위젯은 기록을 저장소에 쓰지 않는다.

정규식은 형식이 정해진 정보만 잡는다. “나는 컴공과 김OO이야” 같은 이름은 못 잡으므로, 서비스 안내문에 “개인정보를 입력하지 말라”고 적는 것도 설계의 일부다.

이 실습의 문서셋

공통 코퍼스의 학과 문서 6개(학과 소개, RAG 교과목, 실습실 규정, 장학금 스캔본, 시간표, FAQ)에 이번 실습용 학과 안내 문서 8개(딥러닝·자연어 처리·MLOps·파이썬 교과목, 도서관, 기숙사, 통학 버스, 학사 행정)를 더했다(assets/data/w13/dept-docs.json). 실제 학과 챗봇처럼 “주말”, “신청”, “선수 과목”, “문의” 같은 말이 여러 문서에 흩어져 있어 생략된 질문이 엉뚱한 문서를 찾기 쉽다. 청크는 4주차 C5처럼 앞에 문서 제목을 붙여 색인한다(“[실습실 이용 규정] …”). 제목이 없으면 “RAG 과목 선수 과목은?”의 “RAG”가 선수 과목이 적힌 청크에 없어 재작성해도 찾지 못한다.

4실습

위젯은 처음부터 “실습실 이용” 대화를 재생한 상태로 열린다. 대화의 각 턴을 두 번 검색한다. (A)는 사용자가 쓴 후속 질문만, (B)는 재작성한 독립 질문으로 BM25 상위 3개를 찾고, 필요한 근거 청크가 들어왔는지(근거 ✓ n위) 표시한다. 두 결과와 재작성 과정, condense 프롬프트는 오른쪽 실행 결과 창에 나온다(휴대폰에서는 위젯 아래). 키가 없으면 답변은 예시 응답 · 수업용 작성 예시(시나리오 턴) 또는 추출식(검색된 문장을 그대로 인용)이다. “벡터 검색도 비교”를 누르면 임베딩 모델(약 118MB)을 받아 벡터 상위 3개도 함께 보여 준다.

관찰 질문

  1. “실습실 이용”의 턴 2 “주말에는?”에서 (A)의 상위 3개는 어떤 문서인가? (A)의 추출식 답과 (B)의 답을 비교한다. 턴 3 “신청은 언제까지 해야 해?”는 (A)도 근거를 2위로 찾는데 왜 여전히 위험한가?
  2. 대화 기록 창을 3 → 2 → 1 → 0으로 줄이며 턴 3과 턴 4의 재작성 결과와 점수판을 본다. 창 1에서 턴 3은 어떤 문서가 1위가 되나? 턴 4가 창 2 이하에서 되묻고 창 3에서 틀리는 이유는?
  3. 턴 4 “거기는 몇 층에 있어?”에서 재작성 방식을 “LLM condense”로 바꾼다. 예시 재작성은 무엇을 “거기”로 보았고, 규칙은 왜 그렇게 못 하나? condense 프롬프트를 펼쳐 모델이 무엇을 보고 답을 알 수 있는지 찾는다.
  4. “RAG 과목” 시나리오의 턴 3 “그럼 딥러닝은?”은 (A)도 딥러닝 문서를 1위로 찾는다. 그런데 (A)의 추출식 답은 무엇인가? 근거 청크를 찾는 것과 질문에 맞는 문장을 고르는 것은 어떻게 다른가?
  5. “되묻기·개인정보” 시나리오에서 턴 1은 왜 되묻고, 턴 2의 학번은 기록과 프롬프트에 어떻게 남았나? “↺ 대화 초기화”를 누른 뒤 “주차장은 어디야?”와 “점심 메뉴 뭐야?”를 차례로 보내 되묻기 기준(τ = 3)이 어느 쪽을 잡는지 확인한다. 초기화하지 않고 보내면 무엇이 달라지나?
  6. (키가 있다면) LLM condense 방식에서 “그럼 자연어 처리는?”처럼 직접 이어서 묻는다. 모델의 독립 질문과 규칙 기반 결과를 비교하고, 모델이 질문에 답해 버리거나 기록에 없는 내용을 넣는 경우가 있는지 본다.

LLM에 보낼 condense 프롬프트를 만든다. 최근 N턴만, 개인정보는 가리고, 챗봇 답변의 인용 번호는 지우고, 글자 예산을 넘으면 오래된 턴부터 뺀다. mockLLM은 실제 모델 대신 규칙 위반을 검사하고 간단히 재작성하는 가짜 함수다. 세 설정 모두 규칙 위반 없이 “학과 행정실 몇 층에 있어?”가 나오게 한다.

const SYSTEM = '너는 학과 안내 챗봇의 질문 재작성기다. 대화 기록과 마지막 질문을 읽고, 기록 없이도 뜻이 통하는 검색용 독립 질문 한 문장으로 다시 쓴다. ' +
  "대명사와 생략된 주제를 기록의 구체적인 이름으로 바꾼다. 답하지 말고 질문만 출력한다. 알 수 없으면 '되묻기: '로 시작한다.";

const turns = [
  { user: '실습실은 몇 시까지 열어?', bot: '실습실은 수업 시간 외에도 평일 오후 9시까지 개방된다 [1].' },
  { user: '내 번호 010-1234-5678로 알림 줄 수 있어?', bot: '알림 기능은 없다. 학과 공지는 홈페이지에서 확인한다.' },
  { user: '주말에는?', bot: '주말과 공휴일에는 사전 신청한 학생만 실습실을 이용할 수 있다 [1].' },
  { user: '신청은 언제까지 해야 해?', bot: '이용일 이틀 전까지 학과 행정실에 신청한다 [1][2].' },
];

// ---- 가짜 LLM (수정하지 않는다): 프롬프트 규칙을 검사한 뒤, 기록에서 가장 최근 장소·주제를 찾아 대명사를 바꾼다
function mockLLM({ system, messages }, { window, maxChars }) {
  const text = messages.map((m) => m.content).join('\n');
  if (!system) throw new Error('system 프롬프트가 없다');
  if (/01[016789]-?\d{3,4}-?\d{4}|20\d{8}/.test(text)) throw new Error('프롬프트에 개인정보가 남아 있다');
  if (/\[\d+\]/.test(text)) throw new Error('챗봇 답변의 인용 번호 [n]이 남아 있다 (재작성에는 필요 없다)');
  const history = text.split('마지막 질문:')[0];
  const userLines = (history.match(/^사용자:/gm) ?? []).length;
  if (userLines > window) throw new Error(`기록이 ${userLines}턴이다. 창 크기 ${window}턴을 넘었다`);
  const lines = history.split('\n').filter((l) => /^(사용자|챗봇):/.test(l)).join('\n');
  if (lines.length > maxChars) throw new Error(`기록이 ${lines.length}자다. 예산 ${maxChars}자를 넘었다`);
  const q = text.split('마지막 질문:')[1]?.split('\n')[0].trim() ?? '';
  const places = [...history.matchAll(/학과 행정실|실습실|도서관/g)].map((m) => m[0]);
  const topic = places[places.length - 1];
  if (/거기|그거/.test(q)) return topic ? q.replace(/거기는|거기서|거기|그거/, topic) : `되묻기: “${q}”에서 무엇을 가리키는지 알려 줄 수 있나?`;
  return topic && !places.some((p) => q.includes(p)) ? `${topic} ${q}` : q;
}

function buildCondensePrompt(turns, question, { window = 3, maxChars = 200 } = {}) {
  // TODO 1: 최근 window턴만 남긴다 (window가 0이면 빈 배열)
  // TODO 2: 각 턴의 user·bot에서 전화번호(010-1234-5678)와 학번(20으로 시작하는 10자리)을 [전화번호] [학번]으로 가린다
  // TODO 3: bot 답변에서 인용 번호 [1], [1][2]를 지운다
  // TODO 4: "사용자: …\n챗봇: …" 줄을 만들고, 기록 전체가 maxChars를 넘으면 가장 오래된 턴부터 뺀다
  const history = '대화 기록: (없음)';
  const content = `${history}\n\n마지막 질문: ${question}\n\n독립 질문:`;
  return { system: SYSTEM, messages: [{ role: 'user', content }] };
}

for (const opts of [{ window: 3, maxChars: 200 }, { window: 1, maxChars: 200 }, { window: 3, maxChars: 60 }]) {
  const prompt = buildCondensePrompt(turns, '거기는 몇 층에 있어?', opts);
  console.log(`--- window=${opts.window}, maxChars=${opts.maxChars}\n${prompt.messages[0].content}`);
  try {
    console.log('→ mockLLM:', mockLLM(prompt, opts));
  } catch (err) {
    console.warn('✗ 규칙 위반:', err.message);
  }
}

6정리 & 다음 주 예고

  • 대화형 RAG는 검색 앞에 한 단계를 더한다. 후속 질문을 대화 기록으로 재작성해 혼자서도 뜻이 통하는 독립 질문으로 만든 뒤 검색한다.
  • 규칙 기반 재작성은 설명할 수 있지만 사전 밖의 주제와 챗봇 답변 속 대상을 못 찾는다. LLM condense는 이를 풀지만 호출이 늘고, 프롬프트에 “답하지 말 것·모르면 되묻기”를 명시해야 한다.
  • 기록 창은 최근 N턴과 글자·토큰 예산으로 자른다. 작으면 주제를 잃고, 크면 비용과 엉뚱한 연결이 는다. 효과는 원문 vs 재작성 hit@3로 잰다.
  • 인용은 턴마다 새로 검색한 출처에만 붙인다. 주제를 모르거나 점수가 낮으면 추측하지 말고 되묻는다. 개인정보는 기록에 넣기 전에 가린다.
