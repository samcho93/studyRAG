1학습 목표

이번 주가 끝나면
  • 검색 평가와 생성 평가를 구분하고, 질문·정답·근거로 이루어진 골든셋 항목을 만들 수 있다.
  • Recall@k, Precision@k, MRR, nDCG@k를 손으로 계산하고 코드로 검산할 수 있다.
  • 골든셋으로 청킹·검색 설정을 비교하고, 12문항 점수의 잡음과 과적합 위험을 설명할 수 있다.

2왜 필요한가

8주차까지 우리는 설정을 바꾸고 질문 한두 개를 던져 결과를 눈으로 확인했다. 이 방식이 얼마나 위험한지 실제 숫자로 본다.

재귀 분할 200자 + BM25로 검색하면 “RAG 수업은 무슨 요일 몇 교시이고 어느 강의실인가?”(q10)의 근거 청크가 12위로 밀려 상위 3개에 들지 않는다. 이 질문 하나만 보고 설정을 고정 길이 100자로 바꾸면 q10의 근거는 1위로 올라온다. 고쳤다고 생각하기 쉽다.

한 문항을 고치는 동안 여섯 문항이 망가졌다

같은 변경을 골든셋 12문항 전체로 채점하면 상위 3개 안에 근거가 들어온 비율(Hit@3)이 0.833 → 0.500으로 떨어진다. 100자 경계에서 근거 문장 다섯 개가 잘렸고(q01·q04·q05·q08·q11), q09는 근거 청크에서 “HNSW”라는 단어가 떨어져 나가 아예 검색되지 않는다.

눈으로 본 한 문항은 좋아졌고 보지 않은 여섯 문항은 조용히 망가졌다. 평가 데이터셋이 없으면 이런 퇴보를 알아챌 방법이 없다. 그래서 RAG 개발은 “같은 골든셋으로 매번 다시 채점한다”는 습관에서 시작한다.

골든셋 만드는 법

골든셋(golden set)은 “이 질문에는 이 근거가 검색되어야 하고, 답은 이것이다”를 적어 둔 평가용 데이터다. 이 과정의 골든셋 assets/data/golden/golden.json의 한 항목은 다음과 같다.

{
  "id": "q01",
  "question": "실습실에서 GPU 서버를 한 사람이 연속으로 쓸 수 있는 최대 시간은?",
  "answer": "최대 12시간이다.",
  "evidence": [{ "doc": "facility-rules",
                 "quote": "한 사람이 연속으로 사용할 수 있는 시간은 최대 12시간이다." }]
}
  • 근거는 문서 id가 아니라 원문 구간(quote)까지 적는다. 그래야 “문서는 맞췄지만 답이 없는 청크”를 걸러 낼 수 있다. quote는 원문에 글자 그대로 있어야 하고, 이것은 코드로 검사한다.
  • 질문은 사용자처럼 쓴다. 원문 문장을 그대로 베낀 질문은 BM25에 유리한 시험 문제가 된다. 우리 골든셋도 “12시간”, “RRF” 같은 단어를 공유하므로 BM25 점수가 후하게 나온다는 점을 기억한다.
  • 쉬운 문항만 모으지 않는다. 표·스캔·중복 문서처럼 망가진 문서(q10~q12), 숫자 답, 여러 문단에 걸친 답을 섞는다. 전부 맞히는 골든셋은 아무것도 구별하지 못한다.
  • 근거가 여러 개면 모두 적는다. 그래야 Recall@k가 “필요한 근거를 몇 개나 모았나”를 제대로 잰다. 우리 골든셋은 문항마다 근거가 1개라 Recall@k와 Hit@k가 같게 나온다.

무엇을 정답으로 칠까: 청크 단위와 문서 단위

검색 결과는 청크다. 청크가 “정답”인지 판정하는 기준이 두 가지 있다.

기준정답 조건특징
문서 단위근거 문서에서 나온 청크면 정답계산이 쉽다. 답이 없는 청크도 정답으로 쳐서 점수가 부풀려진다
청크 단위(근거 단위)근거 문장을 온전히 담은 청크만 정답엄격하다. 근거가 청크 경계에서 잘리면 어떤 청크도 정답이 아니다

고정 100자 + BM25를 문서 단위로 채점하면 Hit@3이 1.000, 청크 단위로 채점하면 0.500이다. 같은 검색 결과인데 정답의 정의만 바꿔서 두 배 차이가 난다. 점수를 보고할 때는 반드시 정답 기준을 함께 적는다.

지표를 손으로 계산하기

질문 하나에 대해 검색기가 청크 5개를 순서대로 돌려주었고, 정답 청크는 A와 C 두 개라고 하자.

순위 i청크정답?1 / log₂(i+1)기여(DCG)
1B✗1.0000
2A✓0.6310.631
3D✗0.5000
4C✓0.4310.431
5E✗0.3870
지표뜻계산 (k=3)계산 (k=5)
Precision@k상위 k개 중 정답 비율1/3 = 0.3332/5 = 0.400
Recall@k정답 전체 중 상위 k개 안에 든 비율1/2 = 0.5002/2 = 1.000
Hit@k상위 k개에 정답이 하나라도 있나11
RR (MRR)첫 정답 순위의 역수. 질문들에 대해 평균하면 MRR1/2 = 0.500 (k와 무관)
nDCG@k정답이 위에 있을수록 큰 점수, 이상적 순서 대비 비율0.631 / 1.631 = 0.3871.062 / 1.631 = 0.651

직관을 먼저 잡고 식을 본다. Recall은 “빠뜨리지 않았나”, Precision은 “쓸데없는 것을 섞지 않았나”, MRR은 “첫 정답이 얼마나 위에 있나”를 본다. nDCG는 순위마다 할인율 1/log₂(i+1)을 곱해 더하므로 같은 정답이라도 1위에 있으면 1점, 4위에 있으면 0.431점만 받는다. 이 합(DCG)을 정답을 맨 위에 몰아 둔 이상적인 순서의 합(IDCG)으로 나누면 0~1 사이의 nDCG가 된다.

DCG@k  = Σ(i=1..k) rel_i / log₂(i+1)
IDCG@k = 정답을 1위부터 채웠을 때의 DCG@k      예) 정답 2개 → 1 + 0.631 = 1.631
nDCG@k = DCG@k / IDCG@k

RAG에서는 k를 LLM에 넣을 청크 수로 맞춘다. 3개를 넣을 거라면 Recall@3이 가장 직접적인 지표다. 4위에 있는 근거는 LLM이 보지 못한다.

생성 평가: Faithfulness와 Answer relevance

  • Faithfulness(근거 충실도) — 답변을 주장 단위로 나누고, 각 주장이 검색된 근거로 뒷받침되는 비율이다. 근거에 없는 내용을 말했다면 우연히 사실이더라도 점수가 낮다.
  • Answer relevance(답변 관련성) — 답변이 질문에 실제로 답하는가. “실습실은 오후 9시까지 개방된다”는 근거에 충실하지만 q01의 답으로는 관련성이 낮다.

이 판정을 사람이 하면 느리고 비싸서 LLM에게 맡기는 방법, 곧 LLM-as-judge를 많이 쓴다. 편리하지만 판정자도 모델이라는 점을 잊으면 안 된다.

LLM-as-judge를 쓸 때 주의할 점
  • 흔들린다: 같은 입력에도 판정이 바뀐다. temperature 0, 고정된 프롬프트, 여러 번 실행한 결과로 판단한다.
  • 편향이 있다: 긴 답변, 자기 회사 모델의 문체, 먼저 제시된 답을 선호하는 경향이 알려져 있다.
  • 형식을 어긴다: JSON을 요청해도 설명을 덧붙인다. 파싱 실패를 처리하고, 점수 산술은 코드로 다시 계산한다.
  • 사람과 맞춰 본다: 판정 결과 일부를 사람이 직접 채점해 일치율을 확인한 뒤에 믿는다.

숫자를 믿기 전에: 잡음과 과적합

12문항은 적다. 문항 하나가 점수를 1/12 ≈ 0.083만큼 움직인다. Hit@3 = 10/12 = 0.833의 95% 신뢰구간(윌슨 구간)은 대략 0.55~0.95다. 설정 A가 0.833, 설정 B가 0.917이면 “B가 낫다”가 아니라 “1문항 차이, 아직 모른다”가 정확한 해석이다. 실무에서는 최소 수십~수백 문항을 모은다.

골든셋에 맞춰 튜닝하면 과적합(overfitting)이 된다. 12문항 점수가 오를 때까지 설정을 수십 번 바꾸면, 그 설정은 “이 12문항”에 맞춰진 것이지 실제 사용자 질문에 좋은 것이 아니다. 골든셋을 튜닝용(dev)과 최종 확인용(test)으로 나누고, test는 마지막에 한 번만 본다. 그리고 만점이 나오면 기뻐하기 전에 골든셋이 너무 쉬운지 의심한다. 이번 주 위젯의 “큰 청크: 고정 400” 설정이 그 예다.

4실습

아래 점수판은 문서셋 12개를 실제 chunker.js로 자르고, 골든셋 12문항을 BM25·벡터·하이브리드(RRF)로 검색한 뒤 metrics.js로 채점한다. 설정을 바꾸면 즉시 다시 채점되고, 결과(요약 점수, 저장한 설정 비교 표, 문항별 결과)는 오른쪽 실행 결과 창에 표시된다. BM25 점수는 바로 나오고, 벡터·하이브리드는 임베딩 모델(최초 1회 다운로드)이 준비되면 채워진다.

문항별 결과에서 ✓는 상위 k개 안에 근거가 있음, ✗는 근거가 k 밖이거나 검색되지 않음, ✂는 근거 문장을 온전히 담은 청크가 아예 없음(청킹 단계의 실패)을 뜻한다. 항목을 펼치면 상위 k개 청크와 근거 위치를 볼 수 있다. 맨 아래 “생성 평가 맛보기”에서는 API 키 없이 휴리스틱으로, 키가 있으면 LLM 판정자로 Faithfulness를 잰다.

관찰 질문

  1. 처음 설정(재귀 200 · BM25 · k=3)에서 실패하는 두 문항은 무엇이고, 근거는 각각 몇 위에 있나? k를 몇까지 올려야 둘 다 성공하나? 그때 LLM에 넣어야 하는 청크 수는?
  2. “실패 재현: 고정 100 · 오버랩 0”을 누르고 저장한다. ✂ 표시가 붙은 문항은 몇 개인가? 오버랩을 20으로 올려 다시 저장하고 두 행을 비교한다.
  3. “같은 설정을 문서 단위로 채점”을 누른다. 검색 결과는 그대로인데 점수가 얼마나 바뀌나? 어느 쪽 숫자를 보고서에 써야 하나?
  4. “큰 청크: 고정 400”은 만점이 나온다. 우리 문서가 대부분 400~550자라는 점을 떠올리면, 이 만점은 무엇을 뜻하나? 이 설정이 실제로 좋은 설정인가?
  5. 검색 방식을 벡터와 하이브리드로 바꿔 각각 저장한다. BM25와의 차이는 몇 문항인가? 이 차이를 “벡터가 낫다(또는 못하다)”의 근거로 삼아도 되나? 영어 전용 모델로 바꾸면 어떻게 되나?
  6. “생성 평가 맛보기”에서 q12를 고르고 “근거에 없는 주장 섞기”를 넣는다. 휴리스틱과 LLM 판정(저장된 예시)이 다른 이유는 무엇인가? q09·q11의 “충실한 답변”이 휴리스틱에서 근거 없음으로 나오는 이유도 찾는다.

난이도 순서다. 코드 상자는 직접 고칠 수 있고, ▶ 실행(또는 Ctrl+Enter)을 누르면 결과가 오른쪽 실행 결과 창에 나온다(휴대폰에서는 코드 바로 아래). 코드는 페이지와 분리된 워커에서 돌아가므로 무한 루프가 생겨도 10초 뒤 자동으로 멈춘다. 모든 Challenge는 임베딩 모델과 LLM 없이 동작한다.

C1. 지표 손계산과 검산★

정답이 d2, d5, d9 세 개인 질문에 검색기가 아래 순서로 결과를 돌려주었다. k=5에서 Precision@5, Recall@5, Hit@5, RR, nDCG@5를 먼저 종이에 계산해 mine에 적고, metrics.js의 값과 비교한다.

const k = 5;

6정리 & 다음 주 예고

  • RAG는 검색 평가(근거를 찾아왔나)와 생성 평가(근거대로 답했나)로 나눠 잰다. 검색이 놓친 근거는 생성이 복구하지 못한다.
  • 골든셋은 질문·정답·근거(원문 quote)로 만들고, quote가 원문에 있는지는 코드로 검사한다.
  • Recall@k는 빠뜨림, Precision@k는 섞임, MRR은 첫 정답의 위치, nDCG@k는 순위 전체의 질을 본다. k는 LLM에 넣을 청크 수에 맞춘다.
  • 정답 기준(청크 단위/문서 단위)에 따라 같은 결과의 점수가 두 배까지 달라진다. 점수에는 기준을 함께 적는다.
  • 12문항 점수에서 1문항 차이는 잡음이다. 골든셋에 맞춘 튜닝은 과적합이므로 dev/test를 나눈다. LLM 판정자도 흔들리고 틀린다.
